# ADR-0005: Noise のパターンと入出力を持たないプロトコル実装

- 状態: 採用
- 日付: 2026-11-11
- 関連: ADR-0001（技術スタック）、ADR-0003（同期モデル）、`docs/spec/pairing.md`、`docs/spec/sync.md`、タスク P2-06〜P2-13

## 背景

ADR-0001 と開発計画では、ペア済み端末間の同期チャネルに Noise `KK` を使い、同期セッションを `tokio` の `AsyncRead + AsyncWrite` の上に実装するとしていた。Phase 2 の仕様を詰める過程で、次の 2 点が問題になった。

1. `KK` は、応答側が握手の最初のメッセージを読む前に相手（イニシエータ）の静的鍵を知っている必要がある。ペア済み端末が 3 台以上あると、応答側は誰が接続してきたのか分からないので、平文の識別子を先に送らせるか、全候補を試すことになる。前者は LAN / BLE 上で端末を追跡できる情報を漏らす（脅威モデル G4）。
2. BLE はモバイル側を Kotlin / Swift で実装する。プロトコルの本体が Rust の非同期ランタイムに結びついていると、FFI 越しに使いにくい。

## 決定

1. **同期チャネルは `Noise_IK_25519_ChaChaPoly_SHA256` にする。** イニシエータの静的鍵は応答側の鍵で暗号化して送られるので、応答側は握手の中で相手を特定でき、傍受者には誰が接続したか分からない。応答側は受け取った鍵を端末レジストリで照合する。ペアリングは計画どおり `XXpsk3` を使う。
2. **プロトコルの本体は入出力を持たない形（sans-IO）で実装する。** 握手、枠、同期セッション、ペアリングは「受け取ったバイト列を渡すと、送るべきバイト列と状態が返る」状態機械とし、ソケットもスレッドも時計も内部に持たない。
3. **PoC の入出力は標準ライブラリのブロッキング I/O とスレッドで書く。** `tokio` は導入しない。LAN は `std::net`、探索は `mdns-sd`（自前のスレッドを持つ）を使う。

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| `KK` + 平文の端末識別子 | 識別子が端末の追跡に使える |
| `KK` + 回転する匿名識別子 | 実現できるが、識別子の導出と同期が必要で複雑。`IK` なら不要 |
| `XX`（毎回、静的鍵を交換） | 往復が 1 回増え、BLE で遅い。相手を先に特定できる利点を使えない |
| `tokio` 上の非同期実装 | モバイルの FFI と相性が悪く、金庫側クレートへネットワーク系クレートが入り込む危険も増える。PoC の同時接続数では利点が小さい |

## 結果

- `IK` の最初のメッセージには前方秘匿性がないが、そこにアプリケーションデータは載せないので影響しない。応答側の静的鍵が漏れると、過去の握手からイニシエータの静的公開鍵（端末の特定）が分かる点は残る。
- 状態機械はメモリ上のテストだけで網羅的に検証でき、同じコードを LAN・BLE・モバイル（UniFFI 経由）で使える。
- Phase 3 でデーモン化するとき、同時接続が増えて必要になれば、入出力の層だけを非同期に置き換えられる。プロトコルの実装は変えずに済む。
- ADR-0001 の「LAN 探索 / 通信」の行のうち `tokio` の記述、および「セキュアチャネル」の行の `KK` の記述は、本 ADR で置き換える。

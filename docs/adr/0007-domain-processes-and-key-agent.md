# ADR-0007: 金庫デーモンをドメインごとのプロセスに分け、Windows Hello は鍵エージェントが外から使う

- 状態: 採用
- 日付: 2026-11-15
- 関連: [ADR-0004](0004-process-architecture.md) の 4、[ADR-0006](0006-windows-sandbox.md)、脅威モデル §5.3（G6）、タスク P3-04、`docs/spec/ipc.md` §13

## 背景

ADR-0004 は、TOTP とパスキーをそれぞれ専用のワーカープロセスで扱い、VK-T / VK-K はそのプロセスだけが持つと決めた（脅威モデルの G6: パスワード側の処理・メモリから TOTP / パスキーの鍵素材を取得できない）。PoC までは、1 つのプロセスの中でドメインごとに別のメモリ領域を使っていた。

一方、ADR-0006 で、Windows Hello の資格情報は AppContainer ごとに分かれることが分かった。サンドボックス内の金庫デーモンからは、利用者が外で作った ZeroPass の資格情報が見えない。P3-04 は、Hello を使う部分をどこで動かすかを決めてから設計することになっていた。候補は (A) TOTP・パスキーのワーカーをコンテナの外で動かす、(B) すべてコンテナの中に置き、既存の金庫は鍵をラップし直す、(C) Hello の署名だけを行う補助プロセスを外に置く、の 3 つだった。

## 決定

### 1. 金庫デーモンを 4 種類のプロセスに分ける

すべて同じ実行ファイル `zp-vaultd` で、同じ AppContainer の中で動く（子プロセスは親のコンテナを引き継ぐ）。

| プロセス | 持つ鍵 | 寿命 |
|---|---|---|
| **フロント**（クライアントが接続する） | VK-P だけ | デーモンと同じ |
| **TOTP ワーカー** | VK-T だけ | 最初に必要になったときに起動し、デーモンと同じ |
| **パスキーワーカー** | VK-K だけ | 同上 |
| **全体プロセス** | すべて | 1 つの操作のあいだだけ |

- フロントは、要求を、そのドメインの鍵を持つプロセスへ渡す。アイテムのドメインは平文のメタデータなので、フロントが鍵なしで調べられる。
- すべてのドメインの鍵を同時に要する操作（金庫の作成・復旧・参加、ペアリングでの迎え入れ、復旧キットの作成、端末の失効）は、そのたびに全体プロセスを起動して行う。操作が終われば、全体プロセスは鍵ごと終了する。ペアリングのオファーを出しているあいだは、オファーの期限まで残る（施錠・新しいオファー・期限切れで終了する）。
- フロントと他のプロセスは、無名パイプ（子プロセスの標準入出力）でつながる。コンテナの中では他の種類のパイプを作れないためでもある。その上のメッセージはデーモンの内部のもので、IPC の仕様（`ipc.md`）には含めない。
- 各プロセスは自分で金庫ファイルを開き、自分の自動施錠の時計を持つ。鍵の更新（失効による鍵の交換など）は、金庫ファイルを通じて各プロセスが追いかける。

### 2. 鍵は、受け取るプロセスに封をして渡す

解錠済みのドメインを別のプロセスへ移すとき（たとえば全体プロセスへ）、持っているプロセスは、スロットの鍵を、受け取るプロセスがその場で作った X25519 の公開鍵に封をして渡す（`ipc.md` §13.3）。フロントは封をされたものを中継するだけで、中身を読めない。

### 3. Windows Hello は、サンドボックスの外の鍵エージェントが使う（案 C）

- 新しい実行ファイル `zp-keyagent` を置く。UI（`zp-cli`）が、Hello の要る操作（TOTP・パスキーの解錠、金庫の作成・復旧・参加）のときだけ起動する。エージェントは金庫デーモンに IPC で接続し、中継を開いたまま待つ。
- 金庫デーモンのプロセスが Hello の署名を要するとき、フロント経由でエージェントに頼む。エージェントは 32 バイトのチャレンジにだけ署名し（それ以外は拒否する）、署名を、頼んだプロセスがその場で作った鍵に封をして返す。署名を開けるのは頼んだプロセスだけである。
- 金庫デーモンは `zp-hwkey` に依存しなくなった。Hello の API を呼ぶのはエージェントだけである。
- 鍵エージェントとして接続できるのは、デーモンと同じディレクトリの `zp-keyagent` だけである（`ipc.md` §5）。他のクライアントが自分の知っている署名を返せば、Hello なしでハードウェアのスロットを開けてしまうためである。

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| (A) TOTP・パスキーのワーカーをコンテナの外で動かす | 金庫鍵を持つプロセスが、OS によるネットワークの禁止の外に出る。ADR-0004 の「金庫鍵を持つプロセスはネットワークを使えない」を、ビルドの検査だけで守ることになる |
| (B) すべてコンテナの中に置き、既存の金庫は一度だけラップし直す | コンテナの中から Hello の確認画面が出るかを確かめられていない。資格情報がコンテナのプロファイルに結び付き、コンテナを作り直すと TOTP・パスキーを開けなくなる。既存の金庫の移行が要る |
| ワーカーを置かず、1 つのプロセスの中で領域を分ける（PoC のまま） | 同じプロセスのメモリが読まれれば、すべてのドメインの鍵が出る。G6 を満たさない |
| 鍵エージェントを常駐させる | 確認画面を出せる UI がいないときにエージェントだけがいても、利用者は応えられない。必要なときに UI が起動する形で足りる |

## 結果

- **確かめたこと**: `bins/zp-cli/tests/isolation.rs` が、実際のデーモン（サンドボックス内）のプロセスのメモリを、同じ利用者のプログラムができる方法で読む。パスワードと TOTP を解錠し、復旧キットを作った（全体プロセスがすべての鍵を持った）あとで、フロントには VK-P があり、VK-T も TOTP のシードも（クライアントが送った base32 の形でも）ない。VK-T は 1 つのワーカーにだけあり、そのワーカーに VK-P はない。施錠すると、どのプロセスにもない。
- **既存の金庫が、サンドボックス内のデーモンで開けるようになるはずである**: エージェントはコンテナの外で動くので、利用者の（コンテナに属さない）資格情報を使う。P3-03 より前に作った金庫と、`--no-sandbox` で作った金庫がこれに当たる。逆に、#55 から本変更までのあいだにサンドボックス内のデーモンが Hello で作った金庫があれば、その資格情報はコンテナのものなので、開けない（その期間に Hello での作成が成功したかは確かめられていない）。
- **実機で確認した（2026-11-15）**: エージェントから Hello の確認画面が出て、署名が返る。P3-03 より前に作った金庫の TOTP が、サンドボックス内のデーモンで開けた。新しい金庫の作成（確認画面 2 回）と、施錠後の解錠（1 回）も通った。エージェントの「動的コードの禁止」（`hardening.md`）は Hello と両立する。生体認証の操作が要るため、自動テストにはしていない。
- **限界**:
  - 防ぐのは、フロントのメモリが読まれること（ダンプ、メモリの読み出し）である。フロントが乗っ取られて任意のコードを実行された場合は防げない。乗っ取ったフロントは、解錠中のワーカーに、自分の鍵へ封をして鍵を渡させることができる。
  - 封は送り手を認証しない。中継するプロセスが受け手の公開鍵をすり替えれば読める（`ipc.md` §13.4）。上と同じく、乗っ取りには効かない。
  - 同じ利用者のプログラムは、プロセスのアクセス制御リストを書き戻して、どのプロセスのメモリも読める（`hardening.md` §3）。分割は、1 回の読み出しで得られるものを 1 つのドメインに限る。
  - プロセスの起動の分だけ、すべてのドメインを要する操作が遅くなる（数十ミリ秒）。
- macOS・Linux でも同じ構成で動く（パイプと子プロセスだけを使う）。鍵エージェントは、それぞれのハードウェア鍵ストアを実装するときに対応させる（P6-09、P6-10）。（追記 2026-11-23: Linux のハードウェア鍵ストアは保留にした。Linux では TOTP とパスキーのドメインを作らない。`.claude/PLAN.md` の P6-10）

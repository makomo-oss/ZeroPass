# ADR-0003: 同期モデル

- 状態: 採用
- 日付: 2026-11-11
- 関連: PLAN §2.3、脅威モデル §5.2、タスク P2-01〜P2-19

## 背景

サーバーを持たないため、同期は端末同士が近接したときに不定期・断続的に行われる。どの端末も長期間オフラインになりうるうえ、接続順序も保証されない。また同期層（`zp-syncd`）は金庫鍵を持たず、暗号文のまま扱える必要がある（ADR-0004）。

## 決定

1. **暗号文 oplog。** 各端末はアイテムの作成・更新・削除ごとに op を追記する。op は `(device_id, seq)` で一意に識別し、`seq` は端末ごとに単調増加する。op 本体はアイテムの暗号文（ADR-0002 のエンベロープ）で、同期層は復号しない。
2. **op の真正性。** op は送信元端末の Ed25519 端末 ID 鍵で署名し、受信側はペア済み端末レジストリで検証する。
3. **差分同期。** 接続時にバージョンベクタ（端末ごとの最大 `seq`）を交換し、相手が持っていない op だけを送る。
4. **競合解決はアイテム単位の LWW。** 順序はハイブリッド論理時計（HLC）で決め、同値なら `device_id` で決定的に比較する。負けたバージョンは履歴として残し、ユーザーが復元できる。
5. **削除は tombstone。** 全ペア済み端末が観測したことをバージョンベクタで確認できたら GC する。
6. **マージは純粋ロジックとして実装する。** トランスポート（LAN / BLE / テスト用ループバック）に依存させず、proptest で「任意の配送順・重複でも収束する」ことを検証する。
7. **端末失効**時は VK-* をローテーションし、残存端末へ再配布する。失効端末は以後の op を復号できない。

## 検討した代替案

| 案 | 却下理由 |
|---|---|
| Automerge / Yjs などの汎用 CRDT | フィールド単位マージは平文が前提で、同期層が暗号文のまま扱えない。パスワード項目の同時編集はまれで、アイテム単位 LWW＋履歴で実用上十分 |
| 状態ベース同期（全件スナップショット交換） | BLE の帯域では非効率。差分の特定にもハッシュ木などが別途必要 |
| 物理時刻による LWW | 端末の時計ずれで新しい変更が負ける。HLC はずれを吸収しつつ因果順序を保つ |
| フィールド単位 LWW | 平文マージが必要。暗号化粒度をフィールド単位にすると複雑になり、メタデータも増える |

## 結果

- 同期層は平文も金庫鍵も扱わずに済み、`zp-syncd` が侵害されても秘密は漏れない。
- 同じアイテムを 2 端末でオフライン編集すると片方が履歴に回る。UI で「競合あり」を通知して救済する（Phase 4）。
- oplog は単調に増えるため、スナップショットと op の圧縮が将来必要になる。
- op 形式、HLC の詳細、tombstone GC の条件は `docs/spec/sync.md`（P2-01）で定める。

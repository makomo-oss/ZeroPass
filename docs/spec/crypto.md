# ZeroPass 暗号仕様（crypto.md）

- 版: 0.1（ドラフト。G-01 でバージョン 1 として凍結する）
- 関連: [ADR-0002 鍵階層](../adr/0002-key-hierarchy.md)、[脅威モデル](../threat-model.md) §5.3・§5.5
- 実装: `crates/zp-crypto`（プリミティブと鍵型）、`crates/zp-vault`（保存形式）

本書はバイト単位の形式を定める。ここに書かれていない暗号処理を実装してはならない。形式を変えるときは、先に本書を改訂する。

## 1. 記法と定数

- `‖` は連結。整数は断りがなければビッグエンディアン。`u8` / `u64` はビット幅。
- すべての対称鍵は 32 バイト。
- 乱数はすべて OS の CSPRNG（`getrandom`）から取る。

| 名前 | 値 |
|---|---|
| ドメイン ID | `P`（Password）= `0x01`、`T`（TOTP）= `0x02`、`K`（Passkey）= `0x03` |
| `vault_id` | 金庫作成時に生成する 16 バイトの乱数 |
| `device_id` | 端末ごとに生成する 16 バイトの乱数 |
| `item_id` | アイテム作成時に生成する 16 バイトの乱数 |
| `hlc` | `u64`。上位 48 ビットが UNIX 時刻（ミリ秒）、下位 16 ビットが論理カウンタ。詳細は `sync.md`（P2-01） |

## 2. プリミティブ

| 用途 | アルゴリズム | 実装 |
|---|---|---|
| AEAD | XChaCha20-Poly1305（鍵 32、ノンス 24、タグ 16 バイト） | `chacha20poly1305` |
| パスワード KDF | Argon2id v1.3（`0x13`）、出力 32 バイト | `argon2` |
| 鍵導出 | HKDF-SHA256（RFC 5869） | `hkdf`、`sha2` |
| TOTP | HMAC-SHA1 / SHA256 / SHA512（RFC 6238） | `hmac`、`sha1`、`sha2` |
| 定数時間比較 | - | `subtle` |

## 3. 鍵

| 鍵 | 生成 | 寿命 | 保存 |
|---|---|---|---|
| `VK-D`（金庫鍵、D ∈ {P, T, K}） | 乱数 | 金庫の存続期間（端末失効時にローテーション） | キースロット（§6）にラップして保存 |
| `DEK`（アイテム鍵） | 乱数。**アイテムを書き込むたびに新しく生成** | 1 バージョン | `VK-D` でラップしてアイテム行に保存 |
| `KEK-P` | マスターパスワードから導出（§5） | 解錠処理の間だけ | 保存しない |
| `KEK-HW` | ハードウェア鍵ストア内（§7） | 端末の存続期間 | OS / ハードウェアが保持 |
| `RK`（復旧鍵） | 乱数 | ユーザーが紙で保管 | 保存しない（§8） |

規則:

1. `VK-P` / `VK-T` / `VK-K` は互いに独立した乱数であり、他の鍵やマスターパスワードから導出しない。
2. `VK-T` / `VK-K` をパスワード由来の鍵でラップしてはならない。実装は鍵の型にドメインを持たせ、これをコンパイル時に禁止する。
3. 鍵はメモリ上で使用後にゼロ化する。長寿命の鍵（`VK-D`、`KEK-*`）はページロックした専用ページに置く（ベストエフォート。失敗しても動作は継続する）。
4. 鍵は複製（`Clone`）・`Display`・直列化を実装しない。`Debug` 出力は鍵の種類だけを示し、鍵素材を含めない。

## 4. エンベロープ形式（バージョン 1）

AEAD による暗号文はすべて次の形式で保存する。

```
envelope = version(1) ‖ nonce(24) ‖ ciphertext ‖ tag(16)
version  = 0x01
```

- `nonce` は封緘のたびに乱数で生成する。
- AAD（関連データ）はエンベロープに含めず、文脈から再構成する（§4.1）。
- 開封時、`version` が未知なら「未対応バージョン」、長さが 41 バイト未満なら「不正な形式」として拒否する。認証失敗の理由は区別せず、単一の「復号失敗」として返す。

### 4.1 AAD

```
AAD = label ‖ 0x00 ‖ fields
```

`label` は NUL を含まない ASCII 文字列。`fields` は用途ごとに固定長で、次の表のとおり。

| 用途 | 鍵 | 平文 | `label` | `fields` |
|---|---|---|---|---|
| アイテム本体 | `DEK` | 直列化したアイテム | `zeropass/v1/item` | `vault_id(16) ‖ domain(1) ‖ item_id(16) ‖ hlc(8) ‖ device_id(16)` |
| DEK のラップ | `VK-D` | `DEK` | `zeropass/v1/dek-wrap` | アイテム本体と同じ |
| `VK-P` のラップ（パスワード） | `KEK-P` | `VK-P` | `zeropass/v1/vk-wrap/password` | `vault_id(16) ‖ domain(1)` |
| `VK-D` のラップ（復旧鍵） | `KEK-R-D`（§8） | `VK-D` | `zeropass/v1/vk-wrap/recovery` | `vault_id(16) ‖ domain(1)` |
| `VK-D` のラップ（ハードウェア） | §7 | `VK-D` | `zeropass/v1/vk-wrap/hardware` | `vault_id(16) ‖ domain(1)` |

`device_id` はそのバージョンを書き込んだ端末の ID。AAD の束縛により、暗号文を別の金庫・ドメイン・アイテム・バージョンへ移し替えると開封に失敗する。

注: AAD は「行全体を古い内容へ差し戻す」攻撃を防がない。巻き戻しの検出は同期層のバージョンベクタ（`sync.md`）が担う。

## 5. マスターパスワードからの鍵導出

```
pw      = NFKC(マスターパスワード) を UTF-8 で符号化したもの
ikm     = Argon2id(password = pw, salt = kdf_salt, m, t, p, 出力長 = 32)
KEK-P   = HKDF-SHA256(salt = kdf_salt, ikm = ikm, info = "zeropass/v1/kek/password", 出力長 = 32)
```

- `kdf_salt` は 16 バイトの乱数。マスターパスワードを変更するたびに作り直す。
- パラメータ `m`（KiB）、`t`、`p` は `VK-P` のパスワードキースロットに平文で保存する（§6）。

| | `m` | `t` | `p` |
|---|---|---|---|
| 作成時の下限 | 19 MiB（19456 KiB） | 2 | 1 |
| 既定値（較正の出発点） | 64 MiB（65536 KiB） | 3 | 1 |
| 読み込み時に受け付ける上限 | 1 GiB | 64 | 16 |

- **較正**: 金庫の作成時とマスターパスワードの変更時に、`m` = 64 MiB、`p` = 1 のまま、導出が約 500 ms になるよう `t` を 3 以上の範囲で増やす（上限 `t` = 16）。
- 下限未満のパラメータでは金庫を作成しない。上限を超えるパラメータの金庫は、資源枯渇攻撃を避けるため開かない。
- 保存されたパラメータを攻撃者が弱く書き換えても、導出される `KEK-P` が変わって解錠に失敗するだけで、総当たりは容易にならない。
- マスターパスワードは 12 文字以上を要求する。より精密な強度推定は UI 実装時（Phase 4）に追加する。

## 6. キースロット

`VK-D` をラップした結果を「キースロット」と呼び、金庫ファイルに保存する。1 つのドメインに複数のスロットを持てる。

| 種別 | ID | 使えるドメイン | 内容 |
|---|---|---|---|
| パスワード | `0x01` | P のみ | `kdf_salt(16)`、`m`、`t`、`p`、§4 のエンベロープ |
| ハードウェア | `0x02` | T、K | ハードウェア鍵ストアが返す不透明なバイト列（§7） |
| 復旧鍵 | `0x03` | P、T、K | §4 のエンベロープ（§8） |

- マスターパスワードの変更は、新しい `kdf_salt` と較正し直したパラメータで P のパスワードスロットを作り直すだけで、`VK-P` とアイテムは変わらない。
- 解錠状態はドメインごとに独立する。パスワードで開くのは P だけである。

## 7. ハードウェア鍵ストア

`VK-T` / `VK-K` は、ユーザーの生体認証（または OS が同等と認める端末 PIN）を毎回要求するハードウェア鍵でラップする。プラットフォーム差は次のインターフェースで吸収する。

```
wrap(context, secret)    -> blob     # 生体認証を要求してよい
unwrap(context, blob)    -> secret   # 必ず生体認証を要求する
```

- `context` は §4.1 の AAD（`zeropass/v1/vk-wrap/hardware ‖ 0x00 ‖ vault_id ‖ domain`）で、実装は `blob` を `context` に束縛しなければならない（別の金庫・ドメインの `blob` を開けない）。
- `blob` の形式は実装ごとに定める。先頭 1 バイトを実装 ID とする。

| 実装 ID | 実装 | 状態 |
|---|---|---|
| `0x01` | ソフトウェア（テスト・開発専用。生体認証なし） | P1-06 |
| `0x02` | Windows Hello（§7.1） | P1-13 |
| `0x03` | Apple Secure Enclave | P6-06 |
| `0x04` | Android Keystore | P6-02 |

ハードウェア鍵ストアが使えない端末では T / K ドメインを作成・解錠できない。ソフトウェア実装は、明示的に有効化した開発用ビルド・オプションでのみ使える。

### 7.1 Windows Hello

Windows Hello の鍵（`KeyCredentialManager`）は署名専用なので、署名から対称鍵を導出する。

```
blob      = 0x02 ‖ challenge(32) ‖ envelope
signature = Hello鍵による challenge への署名（RSASSA-PKCS1-v1_5 / SHA-256。決定的）
KEK-HW    = HKDF-SHA256(salt = challenge, ikm = signature, info = "zeropass/v1/kek/hardware", 出力長 = 32)
envelope  = §4 の形式。鍵 = KEK-HW、AAD = context
```

- `challenge` はラップのたびに乱数で生成する。
- 署名のたびに Windows Hello の認証ダイアログが出る。署名が決定的であることが前提なので、鍵作成時に同じ `challenge` へ 2 回署名して一致を確認し、一致しなければ（ECDSA など）その鍵を使わない。
- 鍵名は `ZeroPass/<vault_id の 16 進>` とする。TPM のない PC では OS がソフトウェアで鍵を保護するため、保護強度が下がる。この場合の扱いは脅威モデル §8-2 で決める。

## 8. 復旧鍵（リカバリーキット）

全端末を失っても、金庫ファイルのバックアップと紙の復旧鍵があれば復元できるようにする。

```
RK       = 32 バイトの乱数
KEK-R-D  = HKDF-SHA256(salt = vault_id, ikm = RK, info = "zeropass/v1/kek/recovery" ‖ 0x00 ‖ domain(1), 出力長 = 32)
```

- 各ドメインの `VK-D` を `KEK-R-D` でラップし、復旧鍵スロットとして金庫ファイルに保存する。作成には全ドメインの解錠が必要。
- 復旧鍵を作り直すと、古い復旧鍵スロットは置き換えられ、古い紙は無効になる。
- **表示形式**: `RK(32) ‖ check(2)` を Crockford Base32（大文字、`I` `L` `O` `U` を使わない）で符号化した 55 文字を、5 文字ずつ `-` で区切る。`check` は `SHA-256("zeropass/v1/recovery-check" ‖ RK)` の先頭 2 バイト。入力時は小文字、区切りの有無、`O`→`0`、`I`/`L`→`1` の読み替えを受け付ける。
- **復元**: 金庫ファイルと復旧鍵から全 `VK-D` を取り出し、新しいマスターパスワードと新しい端末のハードウェア鍵でキースロットを作り直す。
- 復旧鍵は金庫ファイルのバックアップがなければ役に立たない。バックアップの導線は P4-07 で提供する。

## 9. アイテムの暗号化

書き込み:

1. 新しい `DEK` と、そのバージョンの `hlc` を生成する。
2. `ciphertext  = seal(DEK, AAD_item, 直列化したアイテム)`
3. `wrapped_dek = seal(VK-D, AAD_dek, DEK)`
4. `(item_id, domain, hlc, device_id, wrapped_dek, ciphertext)` を保存する。それまでの現行バージョンは履歴へ移す。

- アイテムの種別（ログイン、メモ、TOTP、パスキー）と全フィールド（タイトル、URL を含む）は暗号文の中に置く。平文で保存するのは `item_id`、`domain`、`hlc`、`device_id`、削除フラグだけである。
- 削除は tombstone（削除フラグを立て、`wrapped_dek` と `ciphertext` を空にした新しいバージョン）として記録する。
- アイテムの直列化は Protocol Buffers（`prost`）。フィールド定義は `crates/zp-vault` のメッセージ型を正とする。

## 10. テストベクタと検証

| 対象 | ベクタ |
|---|---|
| XChaCha20-Poly1305 | draft-irtf-cfrg-xchacha-03 §A.3.1 |
| Argon2id | RFC 9106 §5.3 |
| HKDF-SHA256 | RFC 5869 付録 A |
| TOTP | RFC 6238 付録 B |

加えて、改ざん（1 ビット反転）、AAD の各フィールドの不一致、ドメインをまたぐ開封がすべて失敗することをテストする。パーサ（エンベロープ、アイテム、`otpauth://`）はファジングの対象とする（P1-12）。

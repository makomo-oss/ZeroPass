# ZeroPass 同期仕様（sync.md）

- 版: 0.1（ドラフト。G-01 でバージョン 1 として凍結する）
- 関連: [ADR-0003 同期モデル](../adr/0003-sync-model.md)、[crypto.md](crypto.md)、[脅威モデル](../threat-model.md) §5.2
- 実装: `crates/zp-sync`（型・マージ規則・セッション。入出力を持たない）、`crates/zp-vault`（保存）

端末同士が近くにあるときだけ、断続的に、順不同で接続する。その前提で、すべての端末が最終的に同じ内容に収束することを保証する。同期処理は金庫がロックされたままでも動く。扱うのは暗号文と署名だけで、金庫鍵を必要としない。

## 1. 用語

| 用語 | 意味 |
|---|---|
| 端末 | 1 つの金庫ファイルを持つ主体。16 バイトの `device_id` と Ed25519 の署名鍵を持つ |
| op | アイテムの 1 バージョン（作成・更新・削除）。一度作られたら変更しない |
| `seq` | 端末が自分の op に振る通し番号。1 から始まり、欠番なく 1 ずつ増える |
| バージョンベクタ | 端末ごとに「その端末の op を `seq` いくつまで持っているか」を記録した表 |
| HLC | op の新旧を決めるハイブリッド論理時計（§3） |

## 2. op

### 2.1 フィールド

| フィールド | 型 | 説明 |
|---|---|---|
| `device_id` | 16 バイト | op を作った端末 |
| `seq` | `u64` | その端末での通し番号（1 以上） |
| `item_id` | 16 バイト | 対象アイテム |
| `domain` | `u8` | 鍵ドメイン（`crypto.md` §1）。アイテムのドメインは作成後に変わらない |
| `hlc` | `u64` | このバージョンの時刻印 |
| `key_epoch` | `u32` | `wrapped_dek` を包んだ金庫鍵の世代（§8）。初期値 1 |
| `deleted` | 真偽 | 真なら tombstone（削除の記録） |
| `wrapped_dek` | バイト列 | `crypto.md` §9。tombstone では空 |
| `ciphertext` | バイト列 | `crypto.md` §9。tombstone では空 |
| `signature` | 64 バイト | 作成端末の Ed25519 署名（§2.2） |

`(device_id, seq)` が op の識別子で、同じ識別子の op は内容も同一でなければならない。

### 2.2 署名

```
message   = "zeropass/v1/op" ‖ 0x00 ‖ vault_id(16) ‖ device_id(16) ‖ seq(8) ‖ item_id(16)
            ‖ domain(1) ‖ hlc(8) ‖ key_epoch(4) ‖ deleted(1)
            ‖ SHA-256(wrapped_dek)(32) ‖ SHA-256(ciphertext)(32)
signature = Ed25519(端末署名鍵, message)
```

- 整数はビッグエンディアン。`deleted` は `0x00` / `0x01`。
- 署名により、金庫鍵を持たない者（中継する同期プロセスを含む）は op を偽造・改変できない。本体を持たない tombstone も署名で保護される。
- 受信側は、端末レジストリ（§6）にある作成端末の公開鍵で検証する。検証は金庫がロックされていてもできる。

### 2.3 端末署名鍵の保管

端末署名鍵（Ed25519 のシード 32 バイト）は、その端末の金庫ファイルに、存在する各ドメインの金庫鍵でラップして保存する。

```
blob = seal(VK-D, AAD = "zeropass/v1/device-key" ‖ 0x00 ‖ vault_id ‖ domain ‖ device_id, シード)
```

どれか 1 つのドメインを解錠すれば署名できる。金庫がロックされている端末（盗難時など）では新しい op に署名できない。

## 3. ハイブリッド論理時計（HLC）

```
hlc = unix_ms(48 ビット) << 16 | counter(16 ビット)
```

- **発行**: `hlc = max(現在時刻 << 16, これまでに見た最大の hlc + 1)`。時計が止まったり戻ったりしても単調に増える。
- **受信**: 取り込んだ op の `hlc` を「これまでに見た最大」に反映する。
- **上限**: `hlc` は符号付き 64 ビットに収まる範囲とする。
- **時計ずれの防御**: 受信した op の `hlc` の時刻部分が、受信側の現在時刻より 24 時間以上先なら、その op を拒否する（セッションはエラーで終了する）。時計が大きく進んだ端末の op が全端末の時計を汚染するのを防ぐ。該当端末は時計を直すまで同期できない。

## 4. バージョンベクタ

- 端末 X について値 `n` は「X が作った `seq` 1〜n の op をすべて持っている」ことを表す。記載のない端末は 0。
- op は端末ごとに `seq` の順で取り込む。`seq` がちょうど「現在値 + 1」の op だけを受け入れ、現在値以下の op は重複として無視し、それより先の op は順序違反として拒否する。
- 比較: すべての端末について `a[X] ≤ b[X]` なら `a ≤ b`。どちらも成り立たなければ並行。
- 統合: 端末ごとの最大値。

## 5. マージ規則

アイテムごとに「現在のバージョン」を 1 つ持ち、それ以外のバージョンは履歴に置く。

1. op の順序は `(hlc, device_id)` の辞書式順序で決める。`device_id` はバイト列として比較する。これは全順序である。
2. 新しい op を取り込むとき、そのアイテムの現在のバージョンより順序が大きければ、op を現在のバージョンにして、それまでの現在のバージョンを履歴へ移す。そうでなければ op を履歴へ入れる。
3. アイテムに現在のバージョンがなければ、op が現在のバージョンになる。
4. tombstone も通常のバージョンとして同じ規則に従う。削除より新しい更新があれば、アイテムは復活する。
5. 既存アイテムと `domain` が異なる op は拒否する。

現在のバージョンは「そのアイテムの全 op のうち順序が最大のもの」に常に一致する。したがって、同じ op の集合を持つ端末は、取り込んだ順序や重複にかかわらず同じ状態になる。負けたバージョンは履歴に残り、ユーザーが復元できる。

### 5.1 op の検証

取り込む前に次を確認し、1 つでも満たさなければ拒否する。

- 作成端末がレジストリにある。失効済みの端末でもよい。失効前に作られた op は履歴の一部であり、後から参加した端末にも渡す必要があるためである。失効した端末は同期チャネルを張れない（`pairing.md` §4）ので、新しい op を届ける経路を持たない。
- 署名が正しい。
- `seq` が §4 の順序に合う。
- `hlc` が §3 の範囲内。
- tombstone なら `wrapped_dek` と `ciphertext` が空、そうでなければどちらも空でない。
- `domain` が有効な値で、§5 の規則 5 を満たす。

## 6. 端末レジストリ

金庫に参加している端末の一覧。各端末の金庫ファイルに平文で保存し、同期セッションで交換する。

### 6.1 端末レコード

| フィールド | 説明 |
|---|---|
| `device_id` | 端末 ID |
| `sign_pk` | Ed25519 公開鍵（op の署名検証用） |
| `noise_pk` | X25519 公開鍵（同期チャネルの相手認証用。`pairing.md`） |
| `name` | 表示名（例: 「書斎の PC」）。UTF-8 で 64 バイト以内 |
| `introduced_by` | このレコードに署名した端末の ID |
| `signature` | 紹介端末による署名 |

```
message = "zeropass/v1/device" ‖ 0x00 ‖ vault_id ‖ device_id ‖ sign_pk ‖ noise_pk
          ‖ name の長さ(1) ‖ name ‖ introduced_by
```

- 金庫を作った最初の端末は自分自身を紹介者とする（ルート）。
- 以降の端末は、ペアリングの相手（既存の端末）が紹介者になる。
- 受け取ったレコードは、紹介者が既知で、署名が正しい場合に受け入れる。紹介者がその後に失効していてもよい（紹介の時点では正当だったため）。すでに持っているもの以外の自己紹介レコードは受け入れない。
- 同じ `device_id` で内容の異なるレコードは拒否する。

### 6.2 失効レコード

```
message = "zeropass/v1/device-revoke" ‖ 0x00 ‖ vault_id ‖ device_id ‖ revoked_by
```

- 失効していない任意の端末が署名できる。失効は取り消せない。
- 失効した端末とは同期セッションを張らない。その端末が紹介した端末は引き続き有効とする。
- 限界: 失効が全端末に伝わる前であれば、失効した端末はまだ失効を知らない端末と同期でき、op や端末レコードを渡せる。失効させた後は端末一覧を確認すること。
- 失効にあわせて金庫鍵を更新する（§8）。

### 6.3 限界

レジストリは平文で保存するため、ロック中の金庫ファイルを書き換えられる攻撃者は端末を追加できる。これは金庫ファイル自体を消せる攻撃者と同じ前提であり、ここでは防がない（脅威モデル §5.6）。

## 7. 同期セッション

暗号化チャネル（`pairing.md` の Noise セッション）の上で行う。メッセージは Protocol Buffers で、チャネル上では `長さ(4) ‖ 本体` の枠で区切る。1 メッセージは 1 MiB 以下とし、超えるものは拒否する。

セッションは対称で、両端が同じ手順を実行する。

```
A                                   B
│── Hello ──────────────────────────▶│   プロトコル版、vault_id、device_id
│◀───────────────────────── Hello ──│
│── Devices ────────────────────────▶│   端末レコードと失効レコード
│◀─────────────────────── Devices ──│
│── Vector ─────────────────────────▶│   バージョンベクタ
│◀──────────────────────── Vector ──│
│── KeyUpdates ─────────────────────▶│   金庫鍵の更新（§8）。相手を確かめた後にだけ送る
│◀──────────────────── KeyUpdates ──│
│── Ops（1 回以上、最後は last）────▶│   相手が持っていない op
│◀───────────────────── Ops（複数回）│
│── Done ───────────────────────────▶│   取り込み後のバージョンベクタ
│◀────────────────────────── Done ──│
```

1. **Hello**: プロトコル版が異なる、または `vault_id` が異なる相手とは続行しない。
2. **Devices**: 相手のレジストリを §6 の規則で取り込む。その結果、相手端末が失効済みならセッションを終了する。
3. **Vector**: 相手のバージョンベクタを受け取り、相手が持っていない op を端末ごとに `seq` の昇順で送る。自分が作った op に限らず、他の端末が作った op も中継する。
4. **KeyUpdates**: 手元にある鍵更新（§8.2）をすべて送る。送るものがなくても空のメッセージを 1 つ送る。このメッセージだけは、相手の Devices を取り込んで「相手がレジストリにあり、失効しておらず、チャネルの鍵が一致する」ことを確かめた後に初めて作る。失効した端末に新しい鍵を渡さないためである。受け取った側は署名を検証して保存する（金庫鍵は要らない）。
5. **Ops**: 1 メッセージにつき複数の op をまとめる（目安 256 KiB）。最後のメッセージには `last` を立てる。送る op がなくても、空で `last` を立てたメッセージを 1 つ送る。受け取った側は 1 メッセージを 1 トランザクションで取り込む。
6. **Done**: 相手の `last` 付き Ops まで取り込み、自分の op も送り終えたら、最終的なバージョンベクタを添えて送る。双方が Done を送受信したらセッションは完了する。

各方向のメッセージは必ずこの順序で届かなければならない。順序に合わないメッセージを受け取ったら、セッションを終了する。両方向は独立に進み、冒頭の Hello・Devices・Vector は相手の応答を待たずに続けて送ってよい。KeyUpdates は相手の Devices を受け取るまで送れない。

- 途中で切断されても、取り込み済みの op は有効なまま残る。次のセッションはバージョンベクタの交換からやり直すので、続きから再開される。
- 署名されていない op（移行前のデータなど）は送らない。ある端末の op に未署名のものがあれば、その手前までを送る。
- セッション中に検証エラー（§5.1）が起きたら、その時点でセッションを終了する。

## 8. 金庫鍵の更新（端末の失効）

端末を失効させたら、その端末が以後の op を復号できないように金庫鍵を世代交代する。

### 8.1 世代

- 各ドメインの金庫鍵は世代番号 `key_epoch` を持ち、初期値は 1。op は、自分の `DEK` を包んだ鍵の世代を `key_epoch` として持つ（§2.1）。
- 更新では新しい `VK-D` を生成して世代を 1 つ進める。以後の op は新しい世代の鍵で `DEK` を包む。過去の op は包み直さない（失効端末はそれらをすでに復号できたため、包み直しても意味がない）。
- したがって 1 つのドメインは世代ごとの鍵の集まり（鍵束）を持つ。読むときは op の `key_epoch` の鍵を使い、書くときは §8.4 で選んだ鍵を使う。

### 8.2 鍵更新

世代 `e` の鍵を持つ端末が、次の世代の鍵 `VK-D[e+1]` を生成して次のレコードを作る。

```
wrapped_key = seal(VK-D[e], AAD = "zeropass/v1/vk-rotate" ‖ 0x00 ‖ vault_id ‖ domain ‖ (e+1)(4), VK-D[e+1])
signature   = Ed25519(更新した端末の署名鍵,
                "zeropass/v1/key-update" ‖ 0x00 ‖ vault_id ‖ domain ‖ (e+1)(4) ‖ device_id ‖ SHA-256(wrapped_key))
鍵更新      = (domain, epoch = e+1, device_id, wrapped_key, signature)
```

- `VK-D[e]` は、その端末が持つ最も新しい世代の鍵である。
- 鍵更新は金庫ファイルに残し、同期セッションの KeyUpdates（§7）で他の端末へ渡す。受け取った端末は、署名者がレジストリにあることと署名を検証して保存する。保存に金庫鍵は要らないので、ロック中でも（同期デーモンでも）受け取れる。
- 後から失効した端末が署名した鍵更新も有効として扱う。古い鍵から新しい鍵へたどる唯一の道である場合があるためである。
- 鍵更新は、**握手とレジストリの照合を終えた、失効していない相手にだけ**送る。失効端末は古い鍵を持っているので、鍵更新を入手できれば新しい鍵を得られる。これを防いでいるのはチャネルの相手認証である。

### 8.3 鍵束の組み立て

端末のキースロット（`crypto.md` §6）は、鍵束のうち 1 本の鍵とその世代を保持する。ドメインを解錠するとき、および解錠中に鍵更新や失効が届いたときに、スロットの鍵から次の 2 種類のレコードをたどれるだけたどって鍵束を作る。

| レコード | 内容 | 用途 |
|---|---|---|
| 鍵更新（§8.2） | 世代 `e+1` の鍵を世代 `e` の鍵で包んだもの | 古い鍵から新しい鍵へ進む。同期で配る |
| 鍵リンク | 別の世代の鍵を、スロットの鍵で包んだもの | 更新の後にペアリングした端末が、古い世代の op を読む。金庫ファイルの外へは出さない |

```
鍵リンク = seal(スロットの鍵, AAD = "zeropass/v1/vk-chain" ‖ 0x00 ‖ vault_id ‖ domain ‖ 包まれた鍵の世代(4) ‖ スロットの鍵の世代(4), 包まれた鍵)
```

- スロットを作り直す必要はない。マスターパスワードの変更や復旧鍵スロットの作成では、その端末のスロットと同じ鍵を同じ世代のまま包む。したがって、**更新の前に作ったリカバリーキットも引き続き使える**（鍵更新が残っている金庫ファイルと組み合わせる限り）。
- ペアリングでは、既存端末が鍵束の全世代の鍵を渡す（`pairing.md` §3.3）。新端末は書き込み用の鍵をスロットに入れ、それ以外を鍵リンクとして保存する。
- op の `key_epoch` の鍵がまだ届いていなければ、その op は「未着の世代」として読めない。次の同期で鍵更新が届けば読める。

### 8.4 書き込みに使う鍵

1. 鍵束のうち、**失効済みの端末が署名した鍵更新で得た鍵を除いたもの**の中で、世代が最も新しい鍵を使う。
2. 同じ世代に複数あれば、鍵のバイト列が最も小さいものを使う（どの端末も同じ鍵を選ぶ）。
3. 該当する鍵が 1 本もなければ、鍵束全体で 1・2 を適用する。

- 2 台が同時に更新すると、同じ世代に鍵が 2 本できる。どちらの鍵更新も全端末に届き、どちらで書かれた op も読めるので、衝突にはならない。
- 規則 1 は次の攻撃への対策である: 失効したが、まだそれを知らない端末からは信用されている端末が、自分で鍵更新を作って配り、以後の書き込みを自分の知っている鍵でさせようとする。失効が伝わった時点で、その鍵は書き込みに使われなくなる。

### 8.5 失効の手順

1. 失効レコード（§6）を作る。
2. 金庫の全ドメインについて §8.2 の鍵更新を行う。そのため、失効の操作には全ドメインの解錠（マスターパスワードとハードウェア認証）が必要である。1 つでもロックされていれば何も変更しない。
3. 以後、残りの端末は同期のたびに失効レコードと鍵更新を受け取る。失効端末との同期は Devices の時点で打ち切られる。

リカバリーキットからの復元（`crypto.md` §8）は、それまでの全端末を失効させるので、同じく全ドメインの鍵を更新する。

### 8.6 限界

- 失効端末がすでに受け取った op は、失効後も読める。盗難の場合は、保存してあるパスワード自体を変更する必要がある。
- 失効は、各端末がそれを知った時点から効く。失効を知らない端末は、失効端末と同期を続け、鍵更新も渡してしまう。失効の操作をした端末と早く同期させること。
- 鍵更新は金庫ファイルに残り続ける。失効端末が、残っている端末の金庫ファイルそのものを入手した場合、マスターパスワードがなくても新しい世代の鍵を得られる。これを閉じるには、全端末がスロットを新しい世代へ作り直したことを確認してから鍵更新を消す仕組みが要る（将来の課題）。
- 2 台が互いに知らずに別々の端末を失効させた場合、片方の更新が、もう片方で失効した端末に届くことがある（失効を知る前に同期したとき）。規則 8.4 はその鍵を「失効端末が作った鍵」とは見なさないので、両方の失効が全端末に伝わった後に、もう一度更新するのが安全である。

## 9. tombstone の回収（将来）

tombstone と履歴は増え続ける。失効していない全端末のバージョンベクタが、ある tombstone とそのアイテムの全 op を含んでいることを確認できたら、それらを削除してよい。PoC では回収を実装しない。

## 10. 検証

- HLC の単調性、バージョンベクタの比較則と統合則（プロパティテスト）
- 任意の配送順序・重複・中断のもとで、N 台の端末が同じ状態に収束する（プロパティテスト）

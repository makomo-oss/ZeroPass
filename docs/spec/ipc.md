# ZeroPass ローカル IPC 仕様（ipc.md）

- 版: 0.1（ドラフト）
- 関連: [ADR-0004](../adr/0004-process-architecture.md)、[脅威モデル](../threat-model.md) §4（境界 B1・B4）、§6
- 実装: `crates/zp-ipc`、`bins/zp-vaultd`

金庫デーモン `zp-vaultd`（第 1 層）と、同じ端末で動くクライアント（`zp-cli`、デスクトップ UI、`zp-nmh`、`zp-broker`、`zp-syncd`）のあいだの通信を定める。金庫鍵と金庫ファイルを扱うのは vaultd だけで、クライアントはこの IPC を通じて操作を頼む。

## 1. 原則

1. **ネットワークを使わない。** 通信路は Windows の名前付きパイプ、または Unix ドメインソケットに限る。TCP のループバックは使わない（ほかのプロセスや Web ページから届きうるため）。
2. **同じ利用者の、許可された実行ファイルだけが接続できる。** 利用者の一致は OS のアクセス制御で、実行ファイルの一致は接続元プロセスの検査で確かめる（§3）。
3. **鍵は渡さない。** 応答に含めるのは、表示や入力に必要な平文フィールドだけである。金庫鍵、TOTP のシード、パスキーの秘密鍵は、どの応答にも含めない（§6）。
4. **相手ごとに、できることを絞る。** 接続元の実行ファイルから役割を決め、役割ごとに呼べる要求を限る（§5）。

## 2. 通信路

### 2.1 エンドポイント名

金庫ファイル 1 つにつき、デーモン 1 つ、エンドポイント 1 つとする。

```
id = SHA-256("zeropass/v1/ipc" ‖ 0x00 ‖ 金庫ファイルの絶対パス（UTF-8）)[..8] の 16 進表記（16 文字）
```

- Windows ではパスを小文字にしてからハッシュする（ファイル名の大文字小文字を区別しないため）。
- シンボリックリンクは解決しない。同じファイルを別のパスで指定すると、別のエンドポイントになる。

| OS | エンドポイント |
|---|---|
| Windows（サンドボックス内のデーモン。§9） | デーモンが作る名前: `\\.\pipe\LOCAL\zeropass-vaultd-<id>`<br>クライアントが開く名前: `\\.\pipe\Sessions\<セッション ID>\AppContainerNamedObjects\<コンテナの SID>\zeropass-vaultd-<id>` |
| Windows（サンドボックスなしのデーモン） | `\\.\pipe\zeropass-vaultd-<id>` |
| Unix | `<実行時ディレクトリ>/vaultd-<id>.sock` |

Windows のクライアントは、サンドボックスの名前を先に試し、なければサンドボックスなしの名前を試す。どちらで見つけても、§3.2 の検査を行う。

Unix の実行時ディレクトリは `$XDG_RUNTIME_DIR/zeropass`、なければ `<一時ディレクトリ>/zeropass-<uid>`。

### 2.2 アクセス制御

**Windows**

- パイプは `PIPE_REJECT_REMOTE_CLIENTS` 付きで作る（ほかの端末から SMB 経由で開けない）。
- セキュリティ記述子は `D:P(A;;GA;;;<デーモンを動かしている利用者の SID>)`。継承なし、ほかの利用者・Everyone・匿名へのアクセス権なし。
- 最初のインスタンスは `FILE_FLAG_FIRST_PIPE_INSTANCE` 付きで作る。同じ名前のパイプがすでにあれば失敗するので、デーモンの二重起動と、別プロセスが先に作ったパイプへの相乗りの両方を防ぐ。
- クライアントは `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION` を付けてパイプを開く。偽のサーバーに接続してしまっても、サーバーはクライアントになりすまして動けない。

**Unix**

- 実行時ディレクトリは権限 `0700` で作る。すでにある場合は、所有者が自分で、グループとその他に権限がないことを確かめ、そうでなければ使わない。
- ソケットファイルの権限は `0600`。
- 起動時にソケットファイルが残っていたら、接続を試みる。つながればデーモンが動いているので起動をやめ、つながらなければ残骸として消す。

### 2.3 フレーム

```
フレーム = 長さ(4 バイト、リトルエンディアン) ‖ 本体(Protocol Buffers)
```

- 本体の上限は 16 MiB。超える長さを受け取った側は、本体を読まずに接続を閉じる。
- 1 つの接続の上で、クライアントが要求を 1 つ送り、デーモンが応答を 1 つ返す。これを繰り返す。応答を待たずに次の要求を送らない。例外は中継（§11）で、接続ごとに一方向のメッセージが続く。
- 秘密を含みうるので、フレームを組み立てたり受け取ったりしたバッファは、使い終えたら消去する。

## 3. 接続元の検査

### 3.1 デーモンがクライアントを検査する

接続を受けたら、要求を 1 バイトも読む前に次を行う。

1. 接続元のプロセス ID を OS から得る（Windows: `GetNamedPipeClientProcessId`、Linux: `SO_PEERCRED`）。
2. そのプロセスの実行ファイルの絶対パスを得る（Windows: `QueryFullProcessImageNameW`、Linux: `/proc/<pid>/exe`）。
3. パスを許可リストと照合する。載っていなければ、理由（実行ファイルを特定できない、または許可リストにない）を `DENIED` のエラーとして 1 つ送り、接続を閉じる。相手からは何も読まない。載っていれば、その項目の役割（§5）を接続に結び付ける。

許可リストの既定値は「デーモンの実行ファイルと同じディレクトリにある、次の名前の実行ファイル」である。

| 実行ファイル | 役割 |
|---|---|
| `zp-cli`、`zeropass`（デスクトップ UI） | UI |
| `zp-nmh` | 拡張ブリッジ |
| `zp-broker` | Agent Broker |
| `zp-syncd` | 同期 |

パスの比較は、Windows では大文字小文字を区別しない。また Windows では、ドライブ文字を使わないカーネルの名前空間でのパス（`DeviceHarddiskVolume3…`）どうしで比べる。サンドボックス内のプロセスは、ボリュームをドライブ文字に変換できないことがあるためである。

### 3.2 クライアントがデーモンを検査する

クライアントも、要求を送る前に接続先を確かめる。マスターパスワードを偽のデーモンに渡さないためである。

- Windows: `GetNamedPipeServerProcessId` で得たプロセスの実行ファイルが、自分と同じディレクトリの `zp-vaultd` であること。
- Linux: `SO_PEERCRED` で得たプロセスについて、同じことを確かめる。

### 3.3 限界

- **パスの検査は、同じ利用者の権限で動くマルウェアを完全には止めない。** 許可された実行ファイルを書き換えられる、あるいは許可されたプロセスにコードを注入できる攻撃者は、検査を通る。これは脅威モデル §6 の「部分的に防御」の範囲である。インストール先を利用者が書き換えられない場所にすること、実行ファイルの署名を検査することは P3-07 で扱う。
- **macOS では実行ファイルの検査をまだ行わない。** 接続できるのは同じ利用者のプロセスに限られる（§2.2）が、どの実行ファイルかは確かめない。macOS への移植（P6-09）で、コード署名の検査とともに実装する。それまで、macOS では接続元をすべて UI の役割として扱う。
- 検査は接続時に 1 回行う。接続の途中でプロセスが入れ替わることはない（パイプ／ソケットのハンドルはプロセスに属する）。

## 4. メッセージ

Protocol Buffers で定義する。定義の正本は `crates/zp-ipc/src/proto.rs` である。フィールド番号は再利用しない。

### 4.1 接続の開始

接続して最初の要求は `Hello` でなければならない。

| 向き | メッセージ | 内容 |
|---|---|---|
| → | `Hello` | `protocol`（クライアントが話すプロトコルの版。現在 1）、`client`（表示用の名前） |
| ← | `HelloReply` | `protocol`（デーモンの版）、`daemon_version`、`role`（この接続に割り当てた役割） |

版が合わなければ、デーモンは `UNSUPPORTED_PROTOCOL` を返して接続を閉じる。

### 4.2 要求と応答

| 要求 | 応答 | 内容 |
|---|---|---|
| `Status` | `StatusReply` | 金庫の有無、金庫 ID、端末 ID、ドメインごとの状態（あるか、解錠中か）、復旧キットの有無 |
| `CreateVault` | `StatusReply` | マスターパスワードを受け取り、金庫ファイルを作る |
| `RecoverVault` | `StatusReply` | 復旧鍵と新しいマスターパスワードで、金庫へのアクセスを取り戻す |
| `Unlock` | `Done` | ドメインを解錠する。パスワードのドメインはマスターパスワードを添える。TOTP・パスキーのドメインは、デーモンが生体認証を求める |
| `Lock` | `Done` | 1 つのドメイン、またはすべてを施錠する |
| `ListItems` | `Items` | ドメイン内のアイテムの概要（ID、種類、題名、利用者名、URL）。`query` があれば絞り込む。**秘密を含まない** |
| `GetItem` | `Item` | アイテム 1 件の内容（§6 の範囲） |
| `AddItem` | `ItemAdded` | アイテムを追加し、その ID を返す |
| `UpdateItem` | `Done` | アイテムを置き換える |
| `DeleteItem` | `Done` | アイテムを削除する |
| `TotpCode` | `TotpCodeReply` | 現在のワンタイムコードと残り秒数 |
| `ChangeMasterPassword` | `Done` | マスターパスワードを変える |
| `CreateRecoveryKit` | `RecoveryKit` | 復旧キットを作り、復旧鍵を 1 回だけ返す |
| `ListDevices` | `Devices` | 金庫の端末の一覧 |
| `RevokeDevice` | `Done` | 端末を失効させ、金庫鍵を入れ替える |
| `Shutdown` | `Done` | すべて施錠し、デーモンを終了する |

失敗したときは、どの要求にも `Error`（`code`、`message`、該当すれば `domain`）を返す。

- `LOCKED` を受け取ったクライアントは、`domain` を解錠してから同じ要求をやり直せる。
- `message` は人が読むための英語の文で、秘密を含まない。プログラムは `code` で判断する。

### 4.3 予約

次の要求は、この版では定義しない。番号だけを予約する。

| 番号 | 用途 | 定義するタスク |
|---|---|---|
| 48〜63 | 承認要求（Agent Broker の一時許可） | P7-01 |
| 64〜79 | パスキー（`makeCredential` / `getAssertion`） | P5-02 |

## 5. 役割

| 役割 | この版で呼べる要求 |
|---|---|
| UI | すべて |
| 拡張ブリッジ | `Hello`、`Status`（残りは P4-04 で定める） |
| Agent Broker | `Hello`、`Status`（残りは P7-01 で定める） |
| 同期 | `Hello`、`Status`、同期の要求（§10） |

許されない要求には `DENIED` を返す。

## 6. 応答に含めてよい平文

| 種類 | 含める | 含めない |
|---|---|---|
| ログイン | 題名、利用者名、パスワード、URL、メモ | — |
| セキュアノート | 題名、本文 | — |
| TOTP | 発行者、アカウント、桁数、周期、対応するログインの ID、**現在のコード** | **シード** |
| パスキー | RP ID、利用者名 | **秘密鍵**、クレデンシャル ID、ユーザーハンドル |

- TOTP のシードは `AddItem` で入る一方向である（`otpauth://` URI として受け取る）。取り出す要求はない。
- マスターパスワードと復旧鍵は、要求としてクライアントからデーモンへ流れる。復旧鍵は `CreateRecoveryKit` の応答で 1 回だけ逆向きに流れる。

## 7. 解錠の状態

- 解錠の状態はデーモンが持ち、接続をまたいで共有される。ある接続で解錠したドメインは、施錠されるまで、ほかの接続からも使える。
- 自動施錠（`crypto.md`）はデーモンが行う。クライアントが何もしなくても、時間が来れば施錠される。デーモンは 1 秒ごとに期限を調べ、過ぎたドメインの鍵をメモリから消す。
- マスターパスワードを変えると、パスワードのドメインは施錠される。古いパスワードで解錠した状態を、新しいパスワードの下に持ち越さない。
- デーモンが終了すると、すべてのドメインが施錠される。

## 8. デーモンの起動と終了

- **起動**: `zp-vaultd --vault <金庫ファイル>`。金庫ファイルはまだなくてもよい（`CreateVault` で作る）。
- **1 つの金庫に 1 つ**: 同じ金庫ファイルのデーモンがすでに動いていれば、起動せずに終了コード 2 で終わる（§2.2）。
- **クライアントによる起動**: クライアントは、エンドポイントに接続できなければ、自分と同じディレクトリの `zp-vaultd` を起動し、接続できるまで待つ（最長 10 秒）。金庫ファイルがなく、これから作るのでもなければ、起動しない。
  - 起動したデーモンは、クライアントが終了しても動き続ける。コンソール、標準入出力、クライアントが開いているハンドルを引き継がない。
  - 2 つのクライアントが同時に起動を試みても、動き続けるのは 1 つだけである。
- **終了**: `Shutdown` 要求（UI の役割だけが出せる）で、すべてを施錠してから終了する。プロセスを強制終了された場合も、鍵はメモリにしかないので、施錠されたのと同じである。
- ログオン時の自動起動とサービスとしての登録は、インストーラ（P3-07）で扱う。

## 9. サンドボックス

デーモンは、OS のサンドボックスの中で動かす。ネットワークを使えず、金庫に関係のないファイルを開けない状態にするためである。方式の選定と、実機で確かめた内容は [ADR-0006](../adr/0006-windows-sandbox.md) にある。実装は `crates/zp-sandbox`。

| OS | サンドボックス | 状態 |
|---|---|---|
| Windows | capability を持たない AppContainer（名前 `ZeroPass.Vault`） | 実装済み |
| macOS | App Sandbox | P6-09 |
| Linux | seccomp / Landlock | P6-10 |

### 9.1 Windows

クライアントは、デーモンを起動する前に、コンテナに次のアクセス権を与える。これ以外のファイルを、デーモンは開けない。

| 対象 | 与える権限 |
|---|---|
| `zp-vaultd` の実行ファイル | 読み取りと実行 |
| 金庫ファイルのあるディレクトリ | 通過、ファイルの追加。**一覧はできない** |
| そのディレクトリにこれから作られるファイル | 読み取り、書き込み、削除（データベースのジャーナルのため） |
| すでにある金庫ファイル、そのジャーナル、開発用の鍵ファイル | 読み取り、書き込み、削除 |

- ディレクトリにすでにある他のファイルには、権限を与えない。ディレクトリへの付与は、中のファイルへ伝播させない。
- クライアントは接続の前に、自分のプロセスに、コンテナが実行ファイル名を問い合わせるためのアクセス権（`PROCESS_QUERY_LIMITED_INFORMATION`）を足す。これがないと、デーモンは §3.1 の 2 を行えず、接続を閉じる。
- パイプのセキュリティ記述子には、利用者の SID に加えてコンテナの SID を載せる（デーモン自身が、停止のときに自分のパイプを開くため）。
- デーモンは、自分がサンドボックスの中にいるかどうかを `Status` の応答（`sandboxed`）で答える。
- 開発のために、`zp-cli --no-sandbox` はデーモンを通常のプロセスとして起動する。

## 10. 同期の要求

同期デーモン `zp-syncd` は、ほかの端末と同期のプロトコル（`sync.md`）を話すが、金庫ファイルは開かない。送る暗号文を金庫デーモンからもらい、受け取った暗号文を金庫デーモンに渡す。次の要求は、`zp_sync::OpLog` の操作を 1 つずつ IPC に載せたものである。番号は 32〜39。

| 要求 | 応答 | 内容 |
|---|---|---|
| `SyncIdentity` | `SyncIdentity` | 金庫 ID、端末 ID、この端末のチャネル鍵（秘密鍵） |
| `SyncRegistry` | `SyncData` | 端末レジストリ |
| `SyncMergeRegistry` | `SyncMerged` | 相手から受け取った端末レコードと失効を渡す |
| `SyncVector` | `SyncData` | バージョンベクタ |
| `SyncOpsAfter` | `SyncData` | ある端末が書いた op のうち、指定した通し番号より後のもの（件数の上限つき） |
| `SyncApply` | `SyncMerged` | 相手から受け取った op を渡す。全部が保存されるか、1 つも保存されないか |
| `SyncKeyUpdates` | `SyncData` | 鍵更新（`sync.md` §8） |
| `SyncMergeKeyUpdates` | `SyncMerged` | 相手から受け取った鍵更新を渡す |

- レジストリ、バージョンベクタ、op、鍵更新は、同期セッションと同じ符号化（`sync.md` §7）のバイト列として運ぶ。
- **運ばれるのは、暗号文、署名、公開鍵だけである。** 金庫鍵も、アイテムの平文も含まれない。これらの要求は、金庫が施錠されていても使える。
- **金庫デーモンは、渡されたものを信用しない。** op は書いた端末の署名を、端末レコードと失効と鍵更新はそれぞれの署名を、レジストリに照らして検証してから保存する。検証に通らないもの、形式の誤ったものには `SYNC_REJECTED` を返し、何も保存しない。同期デーモンが乗っ取られても、金庫の端末が署名していないデータを金庫に入れることはできない。
- **チャネル鍵**は、この端末であることをほかの端末に示す鍵で、金庫鍵ではない。同期デーモンは、ほかの端末と Noise の握手をするためにこれを持つ。この鍵が漏れると、攻撃者はこの端末になりすまして同期の相手になれる。得られるのは暗号文だけで、署名がないので金庫に書き込むこともできない。
- 同期の役割が呼べるのは、`Hello`、`Status` と、この節の要求だけである。アイテムを読む要求、解錠する要求は `DENIED` になる。
- `zp-cli sync` も同じ要求を使う（UI の役割）。

## 11. ペアリングと中継

ペアリングは、すべての金庫鍵を渡す（既存の端末）、または受け取る（新しい端末）操作なので、金庫デーモンが行う。ただし金庫デーモンはネットワークを使えない。そこで、相手の端末との接続はクライアントが開き、その上を流れるバイト列をクライアントが金庫デーモンとのあいだで**中継**する。流れるのはペアリングチャネル（Noise `XXpsk3`、`pairing.md`）の暗号文なので、中継するクライアントには鍵も許可（grant）も読めない。

### 11.1 要求

| 要求 | 応答 | 内容 |
|---|---|---|
| `PairOffer` | `PairOffered` | ペアリングのオファー（QR コードの文字列）と有効秒数。`hints` に、この端末に届くアドレス（`アドレス:ポート`）を入れる。金庫のすべてのドメインが解錠されていなければ `LOCKED` |
| `PairAdmit` | 中継（§11.2） | `PairOffer` で作ったオファーで、中継する接続の向こうの端末を迎え入れる |
| `PairJoin` | 中継（§11.2） | 相手の端末が示したオファー、この端末の名前、新しいマスターパスワードを渡し、相手から受け取る許可でこの端末の金庫ファイルを作る |

- オファーは 1 つだけ保持し、使われるか期限が切れるまで有効である。新しいオファーを作ると、前のものは無効になる。`PairAdmit` は、成否にかかわらずオファーを使い切る。
- **オファーが待っているあいだ、デーモンは自動施錠を止める。** 相手が接続し、利用者が確認するまでに、ハードウェア鍵のドメインの待ち時間（1 分）を超えうるためである。オファーが使われるか期限が切れると、元に戻す。
- `PairJoin` は、金庫ファイルがまだないときだけ受け付ける。

### 11.2 中継

中継は 2 本の接続を使い、それぞれ一方向にだけメッセージを流す。片方が詰まっても、もう片方を止めないためである。

1. クライアントが `PairAdmit` または `PairJoin` を送る。デーモンは `RelayOpened`（中継の番号）を返す。この接続が**下り**になり、以後はデーモンからクライアントへのメッセージだけが流れる。
2. クライアントは 2 本目の接続を開き、`RelayAttach`（中継の番号）を送る。デーモンは `Done` を返す。この接続が**上り**になり、以後はクライアントからデーモンへのメッセージだけが流れる。1 つの中継に上りは 1 本だけ。
3. 中継のあいだに流れるメッセージ:

| 向き | メッセージ | 内容 |
|---|---|---|
| 下り | `LinkData` | 相手の端末へ送るバイト列 |
| 下り | `PairConfirmRequest` | この端末を加えてよいか、利用者に尋ねる（端末 ID と名前） |
| 下り | `PairDone` | ペアリングの完了。中継の最後のメッセージ |
| 下り | `Error` | 失敗。中継の最後のメッセージ |
| 上り | `LinkData` | 相手の端末から届いたバイト列 |
| 上り | `PairConfirm` | 利用者の答え |

4. 中継が終わると、デーモンは下りの接続を閉じる。クライアントは上りの接続を閉じる。上りが閉じられると、デーモンは相手の端末との接続が切れたものとして扱う。

- `PairConfirmRequest` に 2 分以内に答えがなければ、拒否として扱う。
- `PairDone` には、迎え入れた端末（または自分）の ID と名前、金庫 ID、最初の同期の結果を載せる。最初の同期が終わらなくても、ペアリングは成立している（次の同期で追いつく）。
- 中継を始められるのは UI の役割だけである。

### 11.3 限界

- ペアリングのあいだ（利用者の確認を待つ時間を含む）、デーモンは金庫を使い続けるため、ほかの接続からの要求は待たされる。同期デーモンの同期も、その間は止まる。
- 中継するクライアントは、オファーの文字列を表示するので、使い捨ての秘密（PSK）を知っている。利用者に見せる以上、避けられない。そのため、乗っ取られたクライアントは、自分で用意した偽の端末をデーモンにつなぎ、ペアリングを試みることができる。これを止めるのは、利用者による端末名の確認だけである。ただし、ペアリングを始められるのは UI の役割で、UI はもともとアイテムの平文を読める（§5）。この設計で守るのは、金庫鍵そのものをクライアントのメモリに置かないことである。
- 新しい端末の側では、デーモンが、ペアリングチャネルの相手がオファーに書かれた静的鍵を持つことを確かめる（`pairing.md`）。ネットワークの途中や既存の端末側の中継で、相手をすり替えることはできない。

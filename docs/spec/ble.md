# ZeroPass BLE トランスポート仕様（ble.md）

- 版: 0.1（ドラフト。G-01 でバージョン 1 として凍結する）
- 関連: [lan.md](lan.md)、[pairing.md](pairing.md)、[sync.md](sync.md)、[脅威モデル](../threat-model.md) §5.2
- 実装: `crates/zp-transport`（デスクトップ側）、各モバイルアプリ（Kotlin / Swift）

同じ Wi-Fi にいないとき（外出先、カフェ、テザリングなし）でも、近くにある端末どうしが Bluetooth Low Energy（BLE）だけで同期できるようにする。BLE の上で話す内容は LAN と同じで、`pairing.md` と `sync.md` が定める。本書は、BLE の上にバイト列の通り道（リンク）を作る方法だけを定める。

## 1. 原則

1. **BLE の暗号には頼らない。** BLE のペアリング／ボンディングは使わない。機密性と相手の認証は、リンクの上の Noise チャネル（`pairing.md` §2）がすべて担う。したがって GATT の属性には暗号化や認証の要件を付けない。
2. **名乗らない。** 広告にも GATT の属性にも、利用者・端末・金庫を特定できる値を置かない。置くのは `lan.md` §2 の匿名タグだけである。
3. **リンクは運ぶだけ。** GATT で受け渡すのは、Noise の枠が連なったバイト列をそのまま切り分けたものである。パケットの境界に意味はない。

## 2. 役割

| | GATT の役割 | 理由 |
|---|---|---|
| デスクトップ（Windows / macOS / Linux） | ペリフェラル（サーバー）。広告して接続を待つ | デスクトップは電源につながっており、常時広告できる |
| モバイル（Android / iOS） | セントラル（クライアント）。スキャンして接続する | iOS はバックグラウンドでの広告に強い制約があるが、サービス UUID を指定したスキャンと接続はバックグラウンドでもできる |

- モバイルどうしを BLE で同期する場合は、Android がペリフェラルを兼ねる（将来）。
- GATT の役割と Noise の役割は独立である。同期では常にセントラルが Noise のイニシエータになる。ペアリングでは `pairing.md` §3.1 のとおり、QR コードを読み取った側がイニシエータになる。
- デスクトップが待ち受けをやめるときは、広告の停止を OS に要求したうえで、Tag（§4）を 0 が 16 バイトの値にする。OS が広告をすぐに止めない場合でも、Tag を読んだセントラルは何も送らずに切断する。
- ペリフェラルは同時に 1 台のセントラルとだけリンクを張る。リンク中に別のセントラルが購読しようとしたら、切断する。

## 3. GATT サービス

| 属性 | UUID | プロパティ | 内容 |
|---|---|---|---|
| サービス | `5a50c0de-0001-4b1d-9c5e-7a65726f7061` | — | ZeroPass 近接同期 |
| Tag | `5a50c0de-0002-4b1d-9c5e-7a65726f7061` | Read | §4 の 16 バイト |
| Rx | `5a50c0de-0003-4b1d-9c5e-7a65726f7061` | Write Without Response、Write | セントラル → ペリフェラルのデータ |
| Tx | `5a50c0de-0004-4b1d-9c5e-7a65726f7061` | Notify | ペリフェラル → セントラルのデータ |

### 3.1 広告

- 広告パケットには、接続可能フラグとサービス UUID だけを載せる。端末名（Local Name）は載せない。
- BLE のデバイスアドレスは、OS のプライバシー機能（解決可能なランダムアドレス）に任せる。
- サービス UUID は固定なので、「近くに ZeroPass の端末がある」ことは電波の届く範囲の誰にでも分かる。どの金庫の、どの端末かは分からない。

## 4. Tag キャラクタリスティック

```
value       = sync_tag(8) ‖ pairing_tag(8)
sync_tag    = lan.md §2 の探索タグ（15 分ごとに変わる）
pairing_tag = ペアリングの待ち受け中だけ: SHA-256("zeropass/v1/ble-pairing" ‖ 0x00 ‖ psk)[..8]
              それ以外: 0 が 8 バイト
```

- セントラルは、サービス UUID でスキャンして見つけたペリフェラルに接続し、まず Tag を読む。
  - **同期**: `sync_tag` が端末レジストリのどれかの端末のものでなければ、何も送らずに切断する（別の金庫の端末である）。
  - **ペアリング**: QR コードから得た `psk` で `pairing_tag` を計算し、一致するペリフェラルを選ぶ。一致しなければ切断する。
- タグを広告ではなくキャラクタリスティックに置くのは、広告に任意のデータを載せられない OS があるためである。代償として、近くにある無関係な ZeroPass 端末に一度は接続することになる。
- `pairing_tag` は `psk` から一方向に導出するので、読まれても `psk` は分からない。

## 5. リンク

### 5.1 確立

1. セントラルが接続し、できるだけ大きい ATT MTU を要求する（Android は 517、iOS は OS が決める）。
2. セントラルがサービスを探索し、Tag を読んで相手を確かめる（§4）。
3. セントラルが Tx の通知を購読する（CCCD への書き込み）。ペリフェラルは、購読をもって「リンクが開いた」とみなす。
4. Noise のイニシエータ側が握手の最初のバイト列を送り、`pairing.md` の手順が始まる。

### 5.2 データの受け渡し

- 送る側は、Noise の枠が連なったバイト列を、先頭から `MTU − 3` バイト以下のパケットに切って順に送る。受ける側は、届いた順に連結してそのまま上位へ渡す。パケットごとのヘッダはない。
- セントラル → ペリフェラルは Rx への Write Without Response、ペリフェラル → セントラルは Tx の Notify を使う。
- **送りすぎの防止**: BLE のリンク層は再送と順序を保証するが、ホスト側のバッファがあふれるとパケットが捨てられることがある。送る側は、1 パケットごとに OS の送信完了（Android の `onCharacteristicWrite`、Windows の `NotifyValueAsync` の完了など）を待ってから次を送る。
- それでもパケットが欠けたり入れ替わったりした場合は、Noise の枠の認証が失敗し、チャネルが閉じる（`pairing.md` §2.1）。壊れたデータが取り込まれることはなく、次の機会にやり直す。

### 5.3 終了

- セッションが完了したら、セントラルが購読を解除して切断する。
- どちらかの側で 10 秒間なにも届かなければ、リンクを切る。握手が完了する前の相手には、端末レジストリもバージョンベクタも送らない。

## 6. 同期のタイミング

BLE ではペリフェラルから接続を始められないので、「`device_id` の小さい側が接続する」という `lan.md` §5 の規則は使わない。**常にセントラル（モバイル）が接続する。**

| 状況 | セントラルの動作 |
|---|---|
| アプリを開いている | 30 秒ごとにスキャンし、見つけた端末と同期する。自分に未送信の変更があればすぐにスキャンする |
| バックグラウンド | OS が許す範囲で、サービス UUID を指定したスキャンを続ける。見つけたら同期する |
| 同じ相手と LAN でも届く | LAN を優先し、BLE では接続しない（P2-17） |

デスクトップ側の変更は、次にモバイルが接続してきたときに渡る。

## 7. 性能の見積もり

| 項目 | 目安 |
|---|---|
| 1 パケットの大きさ | MTU 247 のとき 244 バイト、MTU 517 のとき 514 バイト |
| 転送速度 | 接続間隔と OS によるが、おおむね 10〜100 kB/s |
| 数件の変更の同期 | 接続・探索を含めて 2〜5 秒 |
| 1 万件（約 4 MiB）の初回同期 | 1 分〜数分 |

初回同期のような大きな転送は LAN で行うのが望ましい。BLE は日常の差分の同期に使う。実測は P2-18 で行う。

## 8. 脅威と対策

| 脅威 | 対策 |
|---|---|
| 電波の盗聴 | すべて Noise で暗号化する。平文で流れるのは匿名タグだけ |
| 偽のペリフェラル／セントラル | 握手で認証する。握手が成立しない相手には何も渡さない |
| 中継攻撃（遠くの攻撃者が電波を中継する） | 中継されても暗号文が運ばれるだけで、内容の読み取りや改ざんはできない。「近くにいること」自体は認証の条件にしていない |
| 端末の追跡 | アドレスは OS が乱数化し、タグは 15 分で変わる。サービス UUID から「ZeroPass 利用者が近くにいる」ことは分かる |
| 接続の乱発による妨害 | 握手前の相手は 10 秒で切断する。1 台しか同時に受け付けないので、妨害されている間は同期できない（可用性のみの問題） |

## 9. 検証

- 汎用の BLE スキャナアプリから、サービスと 3 つのキャラクタリスティックが見え、Tag が読めて、Rx に書き込め、Tx の通知を受け取れる（P2-15）
- Android のセントラルと Windows のペリフェラルが、Wi-Fi を切った状態でペアリングと同期を完了する（P2-16）
- 送信を意図的に速くしてパケットを欠落させたとき、データが壊れずにセッションが中断する
- 転送速度、ペアリング所要時間、切断からの復帰（P2-18）

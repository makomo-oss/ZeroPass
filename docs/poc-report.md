# ZeroPass PoC レポート（Phase 1・Phase 2）

- 版: 0.3（2026-11-14。パケットキャプチャによる LAN のインターネット遮断の確認を追加）
- 対象: 暗号コア PoC（Phase 1）と近接同期 PoC（Phase 2）
- 用途: ゲート G-01（Go / No-Go）の判断材料

## 1. 結論

設計の 2 つの難所は、どちらも動くことを確認できた。

- **暗号コア**: パスワード、TOTP、パスキーの鍵が互いに独立した金庫が動き、目標の性能（解錠 1 秒未満、1 万件の一覧 100 ms 未満）を満たした。
- **近接同期**: サーバーなしで、同じ Wi-Fi（mDNS + TCP）と Bluetooth LE のどちらでも、端末の追加（ペアリング）と双方向の同期ができた。Windows PC と Android タブレットの実機で、Wi-Fi を切っても Bluetooth だけで同期が続くことを確認した。LAN の通信がリンクの外へ出ないことも、パケットキャプチャで確かめた（§4.5）。
- **Bluetooth の速さ**: 数件の変更の同期は約 3 秒で、日常の差分には十分だった。まとまった転送は約 7 KiB/s と遅く、1 万件の初回同期は約 11 分かかる。初回同期は LAN で行う前提とする（§4.3）。

残っているのは §6 の未確認項目と、§7 の「G-01 で決めること」である。設計を変えなければならない問題は見つかっていない。

## 4. 計測結果

### 4.1 暗号コア（PC）

詳細は [bench/phase1.md](bench/phase1.md)。

| 項目 | 結果 | 目標 |
|---|---|---|
| マスターパスワードでの解錠（較正済み Argon2id） | 542 ms | 1 秒未満 |
| 1 万件の一覧（全件復号） | 61.8 ms | 100 ms 未満 |
| 1 件の追加（ディスク同期込み） | 2.80 ms | — |

### 4.2 ペアリング

| 経路 | 構成 | 所要時間 | 内訳・備考 |
|---|---|---|---|
| LAN | 同じ PC 上の 2 つの金庫（実 LAN インターフェース経由） | 約 0.55 秒 | コード入力から初回同期の完了まで。大半は新しい端末側の Argon2id |
| BLE | PC ⇔ タブレット | 約 3.7〜4.4 秒（2 回） | スキャン 0.4〜0.5 秒、接続から購読まで（MTU 交渉 517、サービス探索、Tag の読み取り）1.0〜1.5 秒、握手・タブレット側の Argon2id・初回同期（3 件）1.9 秒 |

目標は約 3 秒。LAN は満たした。BLE は、スキャンを固定長（4 秒）から「最初の 1 台が見つかって 0.3 秒後に打ち切る」ように変えて 8.5 秒から 3.7〜4.4 秒に縮めたが、わずかに届いていない。残りの大半は接続の確立とタブレット側の鍵導出である。

### 4.3 同期

| 経路 | 構成 | 内容 | 所要時間 |
|---|---|---|---|
| LAN | 同じ PC 上の `zp-syncd` 2 プロセス | 1 件の変更が相手に現れるまで | 接続する側 約 0.9 秒、待つ側 約 3.1 秒（2 秒ごとの問い合わせ） |
| LAN | 同じ PC 上の 2 つの金庫 | 19,446 件（金庫ファイル約 13 MiB）の取り込み | 2.9 秒（mDNS の探索を含む） |
| LAN | PC ⇔ タブレット（Wi-Fi） | アプリの同期操作 1 回（変更 1 件） | 約 3 秒（探索 2.5 秒を含む） |
| BLE | PC ⇔ タブレット（Wi-Fi オフ） | アプリの同期操作 1 回（変更 1〜2 件） | 約 2.9〜3.6 秒（スキャン 0.4〜0.8 秒を含む。スキャン短縮前は 6.4〜6.7 秒） |
| BLE | PC ⇔ タブレット（Wi-Fi オフ） | 500 件（236 KiB）を受け取る | 35 秒（6.7 KiB/s） |
| BLE | PC ⇔ タブレット（Wi-Fi オフ） | 2,000 件（943 KiB）を受け取る | 136 秒（6.9 KiB/s） |

mDNS による発見は、同じ PC 上で約 0.9 秒だった。

BLE の転送速度について:

- 1 秒に約 13 パケット（1 パケット 514 バイト）だった。最後のパケットが届いてから同期が完了するまでは 0.4 秒で、受け取る側の処理は律速になっていない。
- タブレットが短い接続間隔を求める前は 2.3 KiB/s（3,505 件・1,651 KiB に 12 分）だった。求めるようにして約 3 倍になった（`ble.md` §5.2）。
- PC 側で通知を 4 つまで並行して出すようにしても速度は変わらなかったので、その変更は入れていない。
- この速度だと、1 万件（約 4.6 MiB）の初回同期に約 11 分かかる。BLE は日常の差分の同期に使い、初回同期は LAN で行う（`ble.md` §7）。

### 4.4 経路の切り替え

タブレットの Wi-Fi をオン → オフ → オンと切り替えながら、PC の `zp-syncd` を止めずに同期を 3 回行った。経路は LAN → BLE → LAN と切り替わり、毎回、双方の変更が相手に届いた。同じ相手と LAN と BLE の両方で同期することはなかった。

### 4.5 LAN のインターネット遮断（P2-12）

PC の `zp-syncd` の通信（TCP の待ち受けポートと mDNS）を Windows の Packet Monitor で 45 秒間採取し、その間にタブレットが Wi-Fi で 2 回同期した（`scripts/check-lan-capture.ps1`、判定は `zp_transport::capture`）。

| 項目 | 結果 |
|---|---|
| PC が送ったパケット | 370 個（TCP 260、mDNS 110）。Packet Monitor はスタックの層ごとに記録するので、同じパケットを複数回数えている |
| 宛先 | タブレットのアドレスと mDNS のマルチキャスト（`224.0.0.251`）だけ |
| PC が送った TCP の TTL | すべて 1（SYN+ACK と FIN を含む） |
| 判定 | 合格（LAN の外へ向かうパケットは 0 件） |

同じ採取に、タブレットが送ったパケットも入っていた。TCP は SYN を含めて TTL 1 だったが、接続ごとに最後の 1 つ、つまりタブレットが先に閉じた後に PC の FIN に応える ACK だけは、TTL が 64 または 63 だった。閉じたソケットに代わって OS が送るので、ソケットの設定が効かない（§7.2）。

1 回目の採取は判定できなかった。Packet Monitor は Wi-Fi のパケットを 802.11 のフレームのまま記録するが、判定ツールはそれを Ethernet としてしか読めなかった。また、Packet Monitor が記録を始める前に同期が終わっていた。どちらも直した（`lan.md` §6）。

## 5. 障害試験

| 障害 | 方法 | 結果 |
|---|---|---|
| 同期中の切断 | 送信側のリンクを約 1 MB で切る（1,500 件・数 MiB の転送中）。自動テスト | 双方がエラーを検知。受信側には届いたバッチだけが残り、すべて復号できた。次の同期は残りだけを送って完了 |
| 握手中の切断 | リンクを 10 バイトで切る。自動テスト | 何も書き込まれない。次の同期ですべて転送 |
| 同期中の強制終了 | 実バイナリで 2 万件を同期中に、受信側のプロセスを kill | 554 件を書いた時点で停止。金庫ファイルは開け、一覧はバージョンベクタと同じ 554 件。次の同期で残り 19,446 件を取得 |
| 時計ずれ | 24 時間を超えて進んだ時刻印の op を送る。自動テスト | 拒否され、何も保存されない。数分のずれは受け入れ、順序は HLC が保つ |
| 改ざん | op の暗号文を 1 ビット変える、鍵更新の署名を変える。自動テスト | セッションを終了し、何も保存しない |
| 失効端末 | 失効後に同期を試みる、暗号文を直接渡す | 同期は拒否。鍵更新は渡らない。渡された暗号文は復号できない |
| ネットワークの消失と復帰 | タブレットの Wi-Fi の入切（§4.4）、PC 側はアドレスの変化を模した自動テスト | LAN の待ち受けを自動で開き直し、その間も BLE で応答 |

プロセスの強制終了は試したが、OS ごとの電源断（書き込み途中での停電）は試していない。金庫は SQLite を `synchronous = FULL` で使っており、その保証に依存する。

### 5.1 実機の計測中に見つかった不具合（修正済み）

| 不具合 | 起きたこと | 対処 |
|---|---|---|
| Windows に古い GATT サービスが残る | 強制終了した `zp-syncd` のサービスを Windows が残し、次に起動した `zp-syncd` のサービスと並んだ。タブレットが古いほうの Tag を読み、エラー（ATT の Unlikely Error）で同期できなかった | ZeroPass のサービスが複数見えたら、新しく追加されたものから順に試す（`ble.md` §3.2） |
| BLE 同期の後にアプリが異常終了する | 同期は完了するが、その直後にアプリのプロセスが落ちた。Kotlin 側がリンクの終了を伝えるエラーを、UniFFI が Rust 側へ戻せなかった（エラー型が「flat」だった） | エラー型を変え、言語の境界を往復させる回帰テストを追加した |
| 転送が遅い | 既定の接続間隔のままで 2.3 KiB/s だった | 短い接続間隔を求める（§4.3） |

大量の BLE 同期の後に PC 側だけが失敗を記録する問題も見つかった。これは未修正で、§7.2 に記した。

## 7. G-01 で決めること

### 7.1 計画から変えた点（仕様と ADR-0005 に記録済み）

- 同期チャネルの Noise パターンを KK から **IK** に変えた（新しい端末が相手の鍵を事前に持たなくても握手できる）。
- 非同期ランタイム（tokio）を使わず、プロトコルは入出力を持たない状態機械、入出力はブロッキングにした。
- BLE では、回転する匿名タグを広告ではなく GATT のキャラクタリスティックに置いた（広告に任意のデータを載せられない OS があるため）。
- LAN では `device_id` が小さい側だけが接続する。モバイルは常に接続する側になる。
- 鍵のローテーションでは、キースロットを作り直さず、鍵更新をたどる方式にした。更新前のリカバリーキットがそのまま使える。
- モバイルアプリは LAN 同期のために `INTERNET` 権限を持つ（Android にローカルネットワーク限定の権限がないため）。

### 7.2 既知の弱点

- **失効端末による金庫ファイルの入手**: 鍵更新は金庫ファイルに残り続ける。失効した端末が、残っている端末の金庫ファイルそのものを入手すると、その端末のマスターパスワードなしで新しい世代の鍵を得られる（`sync.md` §8.6）。全端末がスロットを新世代へ移したことを確認してから鍵更新を消す仕組みで閉じられる。
- **チャネル鍵の保管**: ロック中も同期できるように、端末のチャネル鍵を金庫ファイルに平文で置いている。Phase 3 で OS の保護領域へ移す予定である。
- **失効の伝わり方**: 失効は、各端末がそれを知った時点から効く。知らない端末は失効端末と同期を続ける。
- **広告の停止**: Windows で広告の停止を要求しても、OS が「広告中」を返し続けた。待ち受けをやめるときはタグを 0 にして、接続してきた相手が何も送らずに切断するようにしている。
- **サービス UUID**: 固定なので、近くに ZeroPass の端末があること自体は電波の届く範囲で分かる（どの金庫の、どの端末かは分からない）。
- **BLE の転送速度**: 約 7 KiB/s で、1 万件の初回同期に約 11 分かかる（§4.3）。新しい端末の追加は、Wi-Fi があれば LAN で行うよう案内する必要がある。モバイルアプリは現在 BLE でしかペアリングしない（§6）。
- **大量の取り込み中の無通信**: 送る側は、すべての op を送った後、相手が取り込み終えるまで何も受け取らない。遅い端末が大量の op（初回同期など）をディスクへ書いている間に、送る側が無通信（既定 30 秒）と判断してセッションを打ち切ることがある。届いた分は残り、次の同期で完了するのでデータは失われないが、取り込み中に進捗を知らせる仕組みが要る。CI の遅いマシンで、試験用に 10 秒へ縮めた制限がこれに当たった。
- **BLE で送る側の待ち始めが早すぎる**: Windows の `NotifyValueAsync` は、パケットを OS のキューに入れた時点で完了する（`ble.md` §5.2）。PC は数秒で「すべて送った」と判断して相手の `Done` を待ち始めるので、無線での転送に 30 秒以上かかると（実測では 500 件以上）、タブレットは正常に完了する一方で、PC 側は無通信として失敗を記録する。データは双方にそろい、失われるのは PC 側の記録だけである。上の「大量の取り込み中の無通信」と同じく、受け取る側が進み具合を一定時間ごとに知らせるメッセージをセッションに加えれば両方を閉じられる。プロトコルの変更になるので、仕様を凍結する前に入れるかどうかを決めたい。
- **接続を閉じた後の最後の ACK の TTL**: 先に接続を閉じた側の OS は、相手の FIN に応える最後の ACK を OS の既定の TTL で送る（§4.5。タブレットで確認、Windows は未確認）。宛先は握手を終えたローカルの相手なのでリンクの外へは出ないが、「すべてのパケットを TTL 1 にする」二重の歯止めは、このパケットにだけ効いていない。閉じるときに `SO_LINGER` を 0 にして FIN の代わりに RST で終えれば、RST はソケットから送られるので TTL 1 になる見込みである（未検証）。セッションはアプリケーションの層で完了を確かめてから閉じるので、RST で終えてもデータは失われない。入れるかどうかを決めたい。

### 7.3 PoC の範囲に入れなかったもの

- モバイル側のハードウェア鍵ストア（TOTP とパスキーは暗号文のまま同期され、タブレットでは開けない）。Phase 6。
- モバイルのバックグラウンド同期と、BLE でのモバイルどうしの同期。
- tombstone と履歴の回収。
- Android アプリのビルドは CI に入っていない（Rust コアとバインディングのテストは CI で実行している）。
- 依存関係の例外: UniFFI が MPL-2.0。UniFFI のバインディング生成ツール経由の `basic-toml` に「メンテナンス終了」の勧告（ビルド時のみ使用）。

### 7.4 リスクの見直し

計画 §5 のリスクのうち、Phase 2 で結論が出たもの:

| リスク | 結論 |
|---|---|
| BLE のペリフェラル実装が OS ごとに別物 | Windows では WinRT で実現できた。macOS・Linux・iOS は未着手。「BLE は発見のみ」への縮退は不要 |
| 自作同期ロジックの収束バグ | プロパティテスト（任意の順序・重複・中断）と実機で収束を確認 |
| 全端末紛失 | リカバリーキットで復元でき、鍵のローテーション後も使える |

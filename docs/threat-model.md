# ZeroPass 脅威モデル

- 版: 0.2（2026-11-14、G-01。Phase 1/2 の PoC の結果を §8・§9 に反映）
- 状態: ドラフト。P8-01 で最終化する。
- 関連: [`.claude/PLAN.md`](../.claude/PLAN.md)、`docs/adr/`、`docs/spec/`

## 1. 目的と前提

ZeroPass は「運営サーバーゼロ」「インターネット非経由の近接同期」「パスワードと 2 段階認証（TOTP）の鍵分離」「OS 非依存パスキー」を設計原則とするパスワードマネージャーである。本書は、何を守り、誰から、どこまで守るのかを定義し、設計と実装の判断基準とする。

前提:

- ユーザーは 1 人が複数端末（PC / スマートフォン）を所有する。共有金庫（家族・チーム）は初期スコープ外。
- 端末の OS・ハードウェア鍵ストア（TPM / Secure Enclave / Android Keystore）は、OS の通常の保証（他アプリのメモリ分離、生体認証の真正性）を満たすものとして信頼する。
- 暗号プリミティブ（XChaCha20-Poly1305、Argon2id、HKDF-SHA256、X25519、Ed25519、P-256）は現在の暗号学的知見のもとで安全とみなす。

## 2. 保護資産

| ID | 資産 | 機密性 | 完全性 | 可用性 | 備考 |
|---|---|---|---|---|---|
| A1 | マスターパスワード | 最高 | - | - | どこにも保存しない。KDF 入力としてのみ一時的にメモリに存在 |
| A2 | 金庫鍵 VK-P（パスワード） | 最高 | 高 | 高 | KEK-P（マスターパスワード由来）でラップして保存 |
| A3 | 金庫鍵 VK-T（TOTP）/ VK-K（パスキー） | 最高 | 高 | 高 | 生体認証必須の HW 鍵でのみラップ。A1 からは導出不能 |
| A4 | 保存データ（ログイン情報、TOTP シード、パスキー秘密鍵、メモ） | 最高 | 高 | 高 | アイテム単位のエンベロープ暗号で保存 |
| A5 | 端末 ID 鍵（Ed25519）/ Noise 静的鍵（X25519） | 高 | 高 | 中 | 端末なりすまし防止の要 |
| A6 | ペア済み端末レジストリ | 中 | 最高 | 中 | 改ざんされると不正端末が同期に参加できる |
| A7 | メタデータ（件数、ドメイン、更新時刻、端末の存在） | 中 | 中 | - | 平文で残すのは item_id・domain 種別・HLC・バージョンのみ |
| A8 | リカバリーキット（復旧鍵） | 最高 | 高 | 最高 | 紙で保管。全端末紛失時の唯一の復旧手段 |
| A9 | AI エージェントに与える一時ログイン許可 | 高 | 高 | - | オリジン束縛・単回・短寿命 |

## 3. 攻撃者モデル

| ID | 攻撃者 | 能力 | 想定 |
|---|---|---|---|
| T1 | リモート攻撃者 | インターネット越しの通信傍受・攻撃 | 防御対象。そもそも同期データはインターネットに流れない |
| T2 | 同一 LAN の攻撃者 | 同じ Wi-Fi 上での盗聴、mDNS なりすまし、中間者攻撃 | 防御対象 |
| T3 | 近接無線の攻撃者 | BLE の盗聴・なりすまし・中継、端末の追跡 | 防御対象 |
| T4 | 端末の窃取・紛失（ロック中） | 端末の物理取得、ストレージの全読み出し、オフライン総当たり | 防御対象 |
| T5 | 同一端末上の非特権マルウェア | ユーザー権限でのファイル読み出し、IPC への接続試行、クリップボード監視 | 部分的に防御（§6 参照） |
| T6 | 悪意ある Web サイト | フィッシング、自動入力の誘導、WebAuthn の悪用 | 防御対象 |
| T7 | 悪意ある／乗っ取られた AI エージェント | プロンプトインジェクション、過剰なログイン要求、秘密の引き出し | 防御対象 |
| T8 | サプライチェーン攻撃者 | 依存クレートの汚染、ビルド・配布物の改ざん | 防御対象（依存監査、再現可能ビルド、署名） |
| T9 | 開発元自身（運営） | アップデート経由での改ざん、データ要求への応答 | 構造的に排除（データを持たない）。アップデート経路は P8-03 で扱う |
| T10 | 解錠中端末の特権マルウェア / OS 侵害 | 管理者・root 権限、カーネル、メモリの任意読み出し | **防御範囲外**（§7） |

## 4. 信頼境界

```
┌──────────────── 端末（信頼: OS とハードウェア鍵ストア） ────────────────┐
│                                                                          │
│  [L1 zp-vaultd]  ←IPC(B1)→  [L2 UI / zp-nmh]  ←Native Messaging(B2)→ [ブラウザ拡張] ←(B3)→ Web ページ
│   ネット権限なし                                                         │
│      ↑ IPC(B4)              [L3 zp-broker] ←stdio MCP(B5)→ AI エージェント
│      │                                                                   │
│  [L4 zp-syncd] ── 暗号文 op のみ                                          │
│      │                                                                   │
└──────┼───────────────────────────────────────────────────────────────────┘
       │ LAN(mDNS+TCP) / BLE GATT  ── Noise 暗号化（B6）
┌──────▼────────── 他のペア済み端末 ──────────┐
```

| 境界 | 越えるもの | 主な脅威 | 主な対策 |
|---|---|---|---|
| B1 vaultd ⇔ ローカルクライアント | API 呼び出し、平文の秘密（UI 表示用） | T5 の不正接続 | 接続元プロセス検証（実行ファイル署名／パス）、セッション鍵、ユーザー単位 ACL |
| B2 ネイティブホスト ⇔ 拡張 | 入力要求、資格情報（入力の瞬間のみ） | 偽拡張 | 拡張 ID 許可リスト、要求ごとのオリジン検証 |
| B3 拡張 ⇔ Web ページ | DOM 操作、WebAuthn 要求 | T6 フィッシング、隠しフィールドへの誘導 | eTLD+1 厳密一致、可視フィールドのみ、ユーザー操作を起点 |
| B4 vaultd ⇔ syncd | 暗号文 op、ペアリング時の鍵配布 | syncd 侵害時の鍵漏洩 | syncd は金庫鍵を持たない。鍵配布は vaultd 内で再ラップ |
| B5 broker ⇔ AI エージェント | ログイン要求、メタデータ | T7 | 秘密を応答に含めない、毎回の生体認証承認、単回許可 |
| B6 端末 ⇔ 端末 | 暗号文 op、ペアリング | T2, T3 | Noise（XXpsk3 / KK）、QR による帯域外認証、静的鍵ピン留め |

## 5. セキュリティ目標と脅威・対策

### 5.1 原則① 運営サーバー完全ゼロ

- **G1**: 開発元はユーザーデータ・メタデータ・端末一覧を一切保持しない。
- 脅威: サーバー侵害（T1, T9）→ 存在しないため不成立。
- 残余リスク: アップデート配布経路（T8, T9）。対策は P8-03（再現可能ビルド、コード署名、署名検証付き更新）。

### 5.2 原則② 完全ローカル近接同期

- **G2**: 同期データはインターネットに出ない。LAN 外宛パケットは 0。
- **G3**: 同期チャネルは盗聴・改ざん・なりすましに耐える。
- **G4**: 第三者が端末の存在を長期間追跡できない。

| 脅威 | 対策 | 検証タスク |
|---|---|---|
| 同期パケットが誤ってインターネットへ（設定ミス、VPN、ルーティング） | プライベート／リンクローカル IF のみ bind、TTL/Hop Limit=1、宛先チェック | P2-12 |
| LAN 上の中間者（ARP / mDNS なりすまし） | Noise KK による相互認証。mDNS の結果は「接続先ヒント」にすぎず信頼しない | P2-08, P2-11 |
| ペアリング時の中間者 | QR で使い捨て 32 バイト秘密と公開鍵指紋を帯域外で渡し、Noise XXpsk3 の PSK に使う。有効期限 60 秒、1 回限り | P2-02, P2-09 |
| BLE の盗聴・中継 | Noise をアプリ層で必ず使う（BLE ペアリングの暗号には依存しない） | P2-14 |
| mDNS / BLE 広告による追跡 | ペア鍵から導出し時間で回転する匿名 ID。端末名・ユーザー名は広告しない | P2-11, P2-14 |
| 悪意あるペア済み端末からの不正 op | op は送信端末の ID 鍵で署名し、AEAD の AAD に item_id・domain・version を束縛 | P2-04 |
| op の再送・巻き戻し | `(device_id, seq)` の単調性とバージョンベクタで重複・巻き戻しを拒否 | P2-05 |
| 失効した端末が同期を続ける | レジストリから削除し、VK-* をローテーションして残存端末へ再配布 | P2-19 |
| 同期が成立しない（DoS、電波妨害） | 可用性は「最終的に同期される」水準とし、ローカルでの読み書きは常に可能 | - |

### 5.3 原則③ 要素分離（パスワードと TOTP の鍵分け）

- **G5**: マスターパスワードが漏洩しても、TOTP シードとパスキー秘密鍵は生体認証なしに復号できない。
- **G6**: パスワード側の処理・メモリから TOTP / パスキーの鍵素材を取得できない。

| 脅威 | 対策 | 検証タスク |
|---|---|---|
| マスターパスワードの漏洩（キーロガー、使い回し） | VK-T / VK-K は A1 から導出せず、生体認証必須の HW 鍵でのみラップ | P1-05, P1-09, P1-13 |
| 鍵の取り違え（実装バグ） | `SecretKey<Domain>` で型レベルにドメインを区別し、取り違えはコンパイルエラー | P1-02 |
| P 側コンポーネントのメモリ漏洩 | ドメインごとに別アリーナ（PoC）→ 別プロセス（Phase 3） | P3-04 |
| 生体認証のバイパス（HW 鍵を使わない経路） | HW 鍵が利用できない端末では TOTP / パスキー機能を無効化。ソフトウェア実装はテスト専用 | P1-06, P1-13 |
| 新端末への VK-T 配布時の盗取 | 配布はペアリング時のみ。送信側で生体認証、Noise チャネル経由、受信側で自端末 HW 鍵へ再ラップ | P2-09 |

注: 「パスワードと TOTP を同じ製品で管理すること」自体が 2 要素の独立性を下げるという批判がある。本設計は、両者の鍵とメモリを分離し、TOTP を生体認証に結びつけることでこれを緩和するが、端末そのものが攻撃者に完全掌握された場合（T10）には両方が失われうる。

### 5.4 原則④ OS 非依存パスキー

- **G7**: パスキー秘密鍵は金庫外に平文で出ず、署名は vaultd のパスキーワーカー内で行う。
- **G8**: RP ID の検証により、他サイト向けのパスキーで署名しない。

| 脅威 | 対策 | 検証タスク |
|---|---|---|
| フィッシングサイトでのパスキー利用 | 拡張が取得したオリジンと RP ID を vaultd 側でも検証 | P5-03, P5-04 |
| 署名鍵の抽出 | 鍵は VK-K でラップし、パスキーワーカーのみが復号 | P5-02 |
| 同期パスキーのクローン検知不能 | signCount は 0 固定（同期型パスキーの慣行）とし、ADR で明記 | P5-03 |

### 5.5 ロック中端末と保存データ（T4）

- **G9**: ロック中端末のストレージを全取得されても、マスターパスワードの総当たり以外に攻撃手段がない。
- 対策: Argon2id（目標 ~500ms、下限パラメータあり）、アイテム単位の AEAD、平文メタデータの最小化、ファイル改ざんは AEAD で検出。
- 残余リスク: 弱いマスターパスワード。作成時に強度を評価し、一定以下を拒否する（P1-09 で扱う）。

### 5.6 同一端末上の非特権マルウェア（T5）

| 脅威 | 対策 | 検証タスク |
|---|---|---|
| vaultd への不正 IPC 接続 | 接続元プロセス検証、ユーザー単位の名前付きパイプ／UDS ACL | P3-01 |
| 金庫ファイルの読み出し | 暗号化済みのため T4 と同等 | - |
| クリップボード監視 | 自動入力を優先し、コピー時は一定時間後に自動消去、クリップボード履歴の除外指定 | P3-06 |
| スワップ・クラッシュダンプへの秘密の流出 | ページロック、コアダンプ無効化、`zeroize` による消去 | P1-02, P3-06 |

### 5.7 Web サイトと自動入力（T6）

- オリジン（eTLD+1）の厳密一致でのみ候補を提示し、自動入力はユーザー操作を起点とする。
- 不可視・画面外のフィールドには入力しない。
- iframe は最上位オリジンと一致する場合のみ入力する。

### 5.8 AI エージェント（T7）

- **G10**: AI エージェントはパスワード文字列・TOTP コード・秘密鍵を一切受け取らない。
- 対策: broker の応答はメタデータ（サイト名、アカウント表示名）のみ。ログインは拡張が対象タブへ直接入力する。許可はオリジン束縛・単回・短寿命で、毎回手元の端末で生体認証を要求する。監査ログを残し、即時取り消しを可能にする。
- 残余リスク: ログイン後のセッションは AI が操作できる。これは「ログイン代行」という機能そのものの性質であり、承認 UI でユーザーに明示する。
- 検証: P7-01〜P7-05（プロンプトインジェクションを想定した悪用テストを含む）。

### 5.9 サプライチェーン（T8）

- 依存は crates.io のみ。cargo-deny（advisories / bans / licenses / sources）と cargo-audit を CI で常時実行する。
- vaultd と暗号・金庫クレートの依存ツリーにネットワーク系クレートが入ったら CI を失敗させる（P0-05）。
- 暗号プリミティブは監査済みの RustCrypto / dalek 実装に限定し、OpenSSL は禁止する。
- `Cargo.lock` をコミットし、CI は `--locked` でビルドする。

## 6. 可用性とリカバリー

サーバーを持たないため、全端末を同時に失うとデータは失われる。これは設計上のトレードオフである。

- リカバリーキット（紙）を初回セットアップで必須の導線とする（P1-14）。
- 2 台目の端末を追加するまで、リカバリーキットの作成をしつこく促す。
- 暗号化エクスポートを提供し、ユーザー自身のバックアップを可能にする（P4-07）。

## 7. 防御範囲外（明示的な非目標）

- **解錠中の端末を管理者／root 権限で掌握したマルウェア、OS・カーネルの侵害（T10）**。メモリ上の解錠済み鍵は取得されうる。被害を解錠中のドメイン（例: P のみ解錠中なら T/K は安全）と解錠時間に限定することを目標とする。
- ハードウェア鍵ストアや生体認証センサー自体の脆弱性。
- ユーザーが自発的に秘密を第三者へ渡すこと、強要。
- 物理的な電波妨害による同期不能（可用性のみの問題）。
- サイドチャネル攻撃のうち、電力解析・電磁波解析など物理アクセスを要するもの。
- 量子計算機による将来の解読（X25519 / Ed25519 / P-256）。同期チャネルのポスト量子化は将来課題とする。

## 8. 未解決事項

初版で「G-01 までに決める」とした事項の、G-01（2026-11-14）時点の状態。

1. **Windows で vaultd のネットワーク権限を OS レベルで剥奪する方式**（AppContainer か WFP か）: 未決。P3-03 で実証して決める。
2. **HW 鍵を持たない端末での TOTP / パスキー**: PoC では機能を無効にする形にした。TOTP とパスキーの暗号文は同期されるが、その端末では開けない（`docs/poc-report.md` §7.3）。マスターパスワードから T・K の鍵を導けないという原則③は保たれる。モバイルの HW 鍵ストアは Phase 6 で実装する。
3. **時計ずれ**: 受信した op の時刻印が 24 時間以上先なら拒否し、数分のずれは HLC が順序を保つ（`sync.md` §3、PoC レポート §5）。TOTP の生成は端末の時計を信頼する。時計のずれた端末への警告は UI（Phase 4・6）で扱う。
4. **匿名 ID の回転と追跡可能性**: LAN と BLE の匿名タグは 15 分ごとに変わり（`lan.md` §2、`ble.md` §4）、BLE のアドレスは OS が乱数化する。BLE のサービス UUID は固定なので、ZeroPass の端末が近くにあること自体は電波の届く範囲で分かる。どの金庫の、どの端末かは分からない（`ble.md` §8）。
5. **アップデート配布方式と「運営サーバーゼロ」の整合**: 未決。P8-03 で決める。

## 9. PoC で分かった残存リスク

詳細は `docs/poc-report.md` §7.2。

- **失効端末による金庫ファイルの入手**: 失効した端末が、残っている端末の金庫ファイルそのものを入手すると、その端末のマスターパスワードなしで新しい世代の鍵を得られる（`sync.md` §8.6）。
- **チャネル鍵の保管**: ロック中も同期できるように、端末のチャネル鍵を金庫ファイルに平文で置いている。金庫ファイルを読める攻撃者（T4）は、その端末として同期に加わり、以後の暗号文と署名済みの op を受け取れる。金庫鍵と端末署名鍵はないので、内容を読むことも op を偽造することもできない（`pairing.md` の鍵の表）。Phase 3 で OS の保護領域へ移す。
- **失効の伝わり方**: 失効は、各端末がそれを知った時点から効く。知らない端末は、失効端末と同期を続ける。
- **最後の ACK の TTL**: 先に接続を閉じた側の OS が送る最後の ACK には、TTL 1 が効かない。宛先はアドレスの検査を通った相手なので、リンクの外へは出ない（`lan.md` §4.4）。
